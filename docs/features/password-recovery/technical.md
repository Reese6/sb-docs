## Proposed solution

Сервис аутентификации ведёт сессии восстановления с ограниченным сроком жизни (BR-001: не более одной активной на пользователя). При запросе восстановления генерируется OTP, сохраняется только его хэш (NFR-002), открытое значение уходит в канал доставки email и нигде не сохраняется. Подтверждение сравнивает хэш введённого кода с сохранённым и считает неверные попытки (BR-003). Успешное подтверждение выдаёт одноразовый `reset_token`, по которому устанавливается новый пароль и завершается сессия.

## Data flow

1. Клиент вызывает `POST /auth/password-recovery` (API-001).
2. Сервис находит учётную запись по email; при отсутствии — отвечает так же, как при наличии (BR-004), без отправки кода.
3. Сервис создаёт или переиспользует активную сессию восстановления (BR-001), генерирует OTP, сохраняет хэш, инициирует отправку email.
4. Клиент вызывает `POST /auth/password-recovery/confirm` (API-002); сервис проверяет код и счётчик попыток (BR-003), при успехе выдаёт `reset_token`.
5. Клиент вызывает `POST /auth/password-recovery/reset` (API-003); сервис обновляет пароль и завершает сессию.

## Transactions

Смена пароля и завершение сессии восстановления выполняются атомарно. Отправка email выполняется вне транзакции; сбой отправки не оставляет сессию в несогласованном состоянии.

## Security

- Хранение только хэша OTP, запрет логирования открытого значения (NFR-002).
- `reset_token` одноразовый, с ограниченным сроком жизни. TBD: срок жизни `reset_token`.
- Защита от перечисления пользователей — единообразный ответ (BR-004, API-005).

## Risks

- Недоставка email пользователю — восстановление невозможно; смягчение: повторная отправка (FR-005).
- Перебор OTP при слабых лимитах; смягчение: BR-003 и rate limits (TBD в api.md).
