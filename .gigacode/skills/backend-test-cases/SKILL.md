# Skill: backend-test-cases

## Когда использовать

Создать или обновить набор воспроизводимых проверок backend-поведения для автотестов: индекс `README.md` и файл на каждый TC. Два режима. Feature: набор `tmp/test-cases/<feature>/`, источники — `requirements.md`, `api/`, `technical.md`, `model/`, `decisions/`. Change: набор `tmp/test-cases/<change-name>/`, источники — `docs/changes/<change-name>/proposal.md` (`Deltas`, `Impact`, `Affected Documents`, `Assigned IDs`) и целевые документы feature; статус change значения не имеет. `ui.md` не источник backend-правил. Набор gitignored и лежит вне `docs/`: не проверяется `scripts/validate-docs.mjs`, вне scope `documentation-review`. Один вызов — одна операция, дельта или явно названный сценарий; вся feature или весь change — очередь. Поводы: подтверждено поведение; нужно покрытие перед автотестами; изменился источник — повторная генерация. Код автотестов, их запуск, продуктовые требования и API-контракт — другие skills (AGENTS.md, «Как определить нужный skill»).

## Вход и стоп-условия

| Проверка | Если не выполнено |
|----------|-------------------|
| Режим назван: feature либо change | Стоп. Показать кандидатов из `docs/features/` и `docs/changes/`, ждать выбора. |
| Вход режима существует: `requirements.md` feature либо `proposal.md` change (в том числе в `archive/`) | Стоп. Ответ: «Нет входа режима — сначала requirements.md (skill `requirements`) либо proposal.md». |
| Метод, сценарий или дельта названы человеком либо однозначно выводятся из входа | Стоп. Показать варианты источников, ждать выбора. Файлы не создавать. |
| Есть источник проверяемого поведения (`requirements.md`, `api/`, `technical.md`, `proposal.md`, слова человека) | Стоп. Ответ: «Нет источников проверяемого поведения» и список недостающих документов. |
| Документ не `approved`, либо правка MINOR, либо apply утверждённого change proposal | Стоп. Ответ: «Содержательное изменение approved-документа — через `change-management`». |

## Прочитать

1. Обязательно: вход режима целиком — `requirements.md` feature либо `proposal.md` change и `requirements.md` каждой feature из его `## Affected Documents`; `README.md` набора, если директория есть; [templates/test-case.md](templates/test-case.md), [templates/test-cases-index.md](templates/test-cases-index.md); [references/coverage.md](references/coverage.md) — направления проверок; [schemas/README.md](../../../schemas/README.md) — формат ID (соглашение, не схема: `tmp/` не валидируется).
2. Если есть: `api/README.md` и нужный файл метода; `technical.md`, `model/`, `decisions/`; `tasks.md` change; `ui.md` — только для согласованности сценария, не как источник backend-правил; файл правимого TC целиком; [references/examples.md](references/examples.md) — учебные примеры формата.
3. Глобальный контекст: `docs/product/business-rules.md`, `docs/product/glossary.md`; правила — по AGENTS.md.

## Правила

Общие — AGENTS.md, `rules/ai-guardrails.md`. Ядро: текст документа, `title` и H1 — русский (заголовки секций — дословно по шаблону; ID, статусы, `TBD`/`ASSUMPTION` — английские); факт — без пометки, только из `requirements.md`, `api/`, `technical.md`, `model/`, `decisions/`, `proposal.md` change или слов человека; неизвестное — `TBD: <что неизвестно>`; предположение — `ASSUMPTION: <текст>. Requires confirmation.`; существующие ID не менять и не переиспользовать.

1. Один сценарий, операция или дельта — один файл `tmp/test-cases/<feature|change-name>/tc-<NNN>-<1-3 слова kebab-case>.md`; номер и имя после создания не менять; за вызов — один кейс и индекс.
2. Новый ID = наибольший `TC-XXX` набора + 1; `grep -rn "TC-" tmp/test-cases/<feature|change-name>/`; нумерация локальна набору.
3. Имя кейса — H1; ID — определение первой строкой тела `- TC-XXX (→ FR-XXX/API-XXX/scenario): <цель>` (иная форма определением не считается).
4. `services/` как источник продуктового поведения не использовать (AGENTS.md).
5. Не изобретать endpoint, таблицу, поле, код ошибки, лимит или SQL-команду; неизвестное — `TBD: <что неизвестно>`.
6. Различать отсутствие поля, `null`, пустую строку, пустой массив и ноль; не подменять одно другим.
7. Однородные значения — таблица вариантов со стабильным ключом, точным входом и своим ожидаемым результатом.
8. Утверждение — форма «объект/путь → сравнение → значение → источник»; для HTTP статуса недостаточно, если контракт определяет body.
9. Неприменимая секция — `Not applicable: <причина>`, не пустая строка и не удаление секции.
10. Повторная генерация сохраняет существующие ID, ручные правки и историю; освободившиеся номера не переиспользуются.
11. Change-режим покрывает дельты вызова и требования, затронутые по `## Impact` и trace-связям; прочее поведение feature не покрывать.
12. Дельта проверяется по `ADDED` и «Станет» `MODIFIED`, не по «Было»; `REMOVED` — по описанному в источнике наблюдаемому отказу. ID в кейсе — как в `proposal.md`: `FR-NEW-1` до apply, реальный ID из `## Assigned IDs` после; статус change не указывать.

## Шаги

1. Определить режим (feature или change) и цель: операция, сценарий или дельта; проверить входы и стоп-условия. Не определено — список вариантов, стоп.
2. Прочитать источники режима и существующие кейсы набора; зафиксировать версии, подтверждения, TBD и конфликты. Если режим change: сверить «Было:» дельты с текущим требованием, расхождение — в открытые вопросы.
3. Построить таблицу проверяемых условий: источник → ожидаемое наблюдаемое поведение; применить [references/coverage.md](references/coverage.md), отметить пробелы. Если режим change: добавить строки регрессии требований из `## Impact`.
4. Директории `tmp/test-cases/<feature|change-name>/` нет — создать её (`mkdir -p`) и `README.md` из [templates/test-cases-index.md](templates/test-cases-index.md).
5. Получить номер: `grep -rn "TC-" tmp/test-cases/<feature|change-name>/` → новый ID = наибольший + 1 (правило 2).
6. Создать или обновить файл кейса из [templates/test-case.md](templates/test-case.md); заполнить секции или `Not applicable: <причина>`. Ссылки — от директории набора: `../../../docs/features/<feature>/…` или `../../../docs/changes/<change-name>/proposal.md`, а не `../requirements.md` из шаблона.
7. Обновить `README.md` набора: таблица кейсов, матрица покрытия, открытые вопросы, очередь операций (change-режим — очередь дельт).

## Примеры

Неправильно — неточное действие и невоспроизводимая проверка:

```text
Передать неверные данные. Получить корректную ошибку.
```

Правильно — точный запрос и проверяемое утверждение с источником:

```text
Действие: POST /example/items, body {}.
Ожидаемый результат: HTTP status equals 422; JSON $.code equals
QUANTITY_REQUIRED (источник: учебный контракт).
```

Неправильно и правильно — ID дельты без proposal и с ним:

```text
- TC-001 (→ FR-NEW-1): выгрузка доступна роли TRANSFORMATION_OFFICE.
- TC-001 (→ FR-NEW-1, proposal export-portfolio): выгрузка доступна роли
TRANSFORMATION_OFFICE (источник: дельта ADDED к requirements.md).
```

## Чеклист

- [ ] Изменён один файл кейса плюс `README.md` набора; директория — по режиму; имя и номер по правилам 1–2.
- [ ] Change-режим: покрыты дельты вызова и регрессия из `## Impact`; ID — как в `proposal.md`.
- [ ] Определение `- TC-XXX (→ …): …` — первой строкой тела; номер не переиспользован.
- [ ] Все секции шаблона заполнены или `Not applicable: <причина>`; ни одна не пустая без TBD.
- [ ] Каждое утверждение результата ссылается на источник; ни одного значения без FR/BR/NFR/API или слов человека.
- [ ] Таблица кейсов и матрица покрытия обновлены; ручные правки и история сохранены.
- [ ] Ни одного выдуманного endpoint, поля, кода ошибки, лимита, таблицы БД или SQL-команды.
- [ ] `services/` не использован как источник продуктового поведения.

## Отчёт

```text
Область: feature <name> | change <name>
Файлы: <созданные и изменённые пути>
ASSUMPTION (ждут подтверждения): <список или none>
TBD (ждут ответа): <список или none>
Тест-кейсы: <добавлены/изменены>; пробелы <список>; валидация <результат>
Следующий шаг: <следующая операция или дельта, уточнение блокеров или .gigacode/skills/documentation-review>
```
