# Skill: data-model

## Когда использовать

Создать или изменить `docs/features/<feature>/model/` — сущности, которые feature использует, вводит и меняет. Директория содержит индекс `README.md` и по файлу на каждую новую или изменяемую сущность; один вызов skill — одна сущность. Единственный skill, описывающий данные на уровне feature. Поводы: в требованиях появились новые данные; изменился состав полей; стадия model оркестратора. Физическая схема, индексы и миграции — `technical-documentation`; глобальные файлы сущностей — `feature-apply`. Остальные документы — другие skills (AGENTS.md, «Как определить нужный skill»).

## Вход и стоп-условия

| Проверка | Если не выполнено |
|----------|-------------------|
| `product.md` и `requirements.md` существуют и заполнены, не только `TBD` | Стоп. Ответ: «Сначала product.md (skill `product-documentation`) и requirements.md (skill `requirements`)». |
| Сущность названа человеком | Стоп. Составить список сущностей из `requirements.md`, показать человеку, ждать выбора. Файлы не менять. |
| Состав полей выводится из `requirements.md` либо назван человеком | Стоп: задать до пяти вопросов одним списком и ждать ответа. Дальше не продолжать. |
| Документ не `approved`, либо правка MINOR, либо apply утверждённого change proposal | Стоп. Ответ: «Содержательное изменение approved-документа — через `change-management`». |

## Прочитать

1. Обязательно: `product.md` и `requirements.md` feature целиком; `model/README.md` feature, если директория есть; [glossary.md](../../../docs/product/glossary.md) — единственный источник имён; [data-model/](../../../docs/architecture/data-model/README.md) и все файлы сущностей в этой директории; [schemas/README.md](../../../schemas/README.md) — frontmatter. Правила — по AGENTS.md.
2. Если есть: файл правимой сущности целиком; `ui.md` feature.
3. Контекст: [business-rules.md](../../../docs/product/business-rules.md).

## Правила

Общие — AGENTS.md, `rules/ai-guardrails.md`. Ядро: текст документа, `title` и H1 — русский (заголовки секций — дословно по шаблону; ID, статусы, `TBD`/`ASSUMPTION` — английские); факт — без пометки, только из `product.md`, `requirements.md`, `docs/architecture/data-model/` или слов человека; неизвестное — `TBD: <что неизвестно>`; предположение — `ASSUMPTION: <текст>. Requires confirmation.`; своих ID у документов нет — только ссылки на FR/BR/NFR.

1. Файл заводится только на новую сущность и на сущность, которую feature меняет. Используемая без изменений — строка-ссылка в секции «Существующие сущности» индекса, своего файла не получает.
2. Один файл — одна сущность. За вызов меняется один файл сущности и индекс `README.md`; другие файлы не трогать.
3. Имя файла — kebab-case, латиница; для существующей сущности совпадает с именем её файла в `docs/architecture/data-model/`. После создания имя не менять.
4. Сначала переиспользование: сущность уже есть в `docs/architecture/data-model/` — она существующая. Совпадение по смыслу под другим именем — тоже переиспользование.
5. Поля существующей сущности не копировать. Источник состава полей — файл сущности в `docs/architecture/data-model/`; в файле feature только секция «Изменения».
6. Изменение существующей сущности — только дельта: `ADDED: <поле> — <тип> — <обязательность> — <зачем>`, `MODIFIED: <поле> — было <как> — стало <как> — <почему>`. Формы `REMOVED` нет: удаление поля — через `change-management`.
7. Имена сущностей и полей — из `glossary.md`. Термина нет — `TBD` и предложить дополнить `glossary.md` отдельно.
8. Тип, обязательность, длина и формат поля — только подтверждённые; иначе `TBD` в ячейке. «По аналогии» значения не выводить.
9. Физическая схема — таблицы, индексы, миграции, выбор хранилища — в `technical.md`, сюда не писать.
10. Файлы в `docs/architecture/data-model/` этот skill не создаёт и не правит: промоут делает `feature-apply` после `approved`.
11. Сущности ID не получают (`schemas/README.md`); идентификатор сущности — имя её файла в kebab-case.
12. Трассируемость: каждая новая сущность и каждое изменение — минимум одна связь с FR или BR, в файле сущности и в индексе. Связи нет — `TBD` и вопрос человеку.
13. Новый файл — `type: model`, `status: draft`, `feature: <feature-name>`; `version`: MINOR без изменения состава сущностей, MAJOR при добавлении или изменении сущности; `approved` после правки → `review`.

## Шаги

1. Прочитать `product.md` и `requirements.md`; выписать данные, которые упоминают FR и BR.
2. Сопоставить каждый выписанный объект с файлами `docs/architecture/data-model/`: совпадение — существующая сущность, иначе кандидат в новые (правила 4–5).
3. Определить сущность вызова: из слов человека. Не названа — показать список кандидатов и остановиться. Состав полей не выводится — задать до пяти вопросов одним списком и остановиться.
4. Директории `model/` нет — создать `model/README.md` из [templates/model-index.md](../../../templates/model-index.md).
5. Сущность используется без изменений — добавить строку-ссылку в «Существующие сущности» индекса; файл не создавать, перейти к шагу 8.
6. Создать файл сущности из [templates/model-entity.md](../../../templates/model-entity.md) по правилу 3; комментарии `<!-- AI: -->` выполнить и удалить. Файл есть — открыть его.
7. Заполнить секции: «Источник», затем «Поля» для новой либо «Изменения» для существующей, «Связи», «Трассируемость»; неприменимая — `Not applicable: <причина>`.
8. Обновить `model/README.md`: строка в таблицах «Сущности feature» и «Трассируемость»; диаграмма `erDiagram` в блоке `mermaid`. Добавить строку `model/` в таблицу Documents файла `README.md` feature, если её ещё нет.
9. Запустить `node scripts/validate-docs.mjs`; добиться exit 0.

## Примеры

Неправильно — поля существующей сущности скопированы в feature, тип выдуман:

```text
### Пользователь
| Поле | Тип | Обязательность | Описание |
| email | string(255) | да | Адрес электронной почты |
```

Правильно — ссылка на файл сущности, дельта, неподтверждённый тип помечен:

```text
Источник: Изменение существующей — [Пользователь](../../../architecture/data-model/user.md).
Изменения: ADDED: reset_token — TBD — TBD — хранит сессию восстановления.
```

## Чеклист

- [ ] Изменён ровно один файл сущности плюс `model/README.md`; имя файла по правилу 3.
- [ ] Сущность без изменений осталась строкой-ссылкой в индексе, файла не получила.
- [ ] Поля существующей сущности не скопированы: в её файле только «Изменения».
- [ ] Новая сущность заведена только там, где подходящего файла в `docs/architecture/data-model/` нет.
- [ ] Имена сущностей и полей — из `glossary.md`; отсутствующий термин помечен `TBD`.
- [ ] Тип и обязательность каждого поля подтверждены или `TBD`; выдуманных значений нет.
- [ ] Физической схемы БД, индексов и миграций в документах нет.
- [ ] «Трассируемость» файла и индекса связывает сущность с FR или BR.
