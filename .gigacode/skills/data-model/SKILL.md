# Skill: data-model

## Когда использовать

Создать или изменить `docs/features/<feature>/model.md` — сущности, которые feature использует, вводит и меняет. Единственный skill, описывающий данные на уровне feature. Поводы: в требованиях появились новые данные; изменился состав полей; стадия model оркестратора. Физическая схема, индексы и миграции — `technical-documentation`; глобальные файлы сущностей — `feature-apply`. Остальные документы — другие skills (AGENTS.md, «Как определить нужный skill»).

## Вход и стоп-условия

| Проверка | Если не выполнено |
|----------|-------------------|
| `product.md` и `requirements.md` существуют и заполнены, не только `TBD` | Стоп. Ответ: «Сначала product.md (skill `product-documentation`) и requirements.md (skill `requirements`)». |
| Состав сущностей выводится из `requirements.md` либо назван человеком | Стоп: задать до пяти вопросов одним списком и ждать ответа. Дальше не продолжать. |
| Документ не `approved`, либо правка MINOR, либо apply утверждённого change proposal | Стоп. Ответ: «Содержательное изменение approved-документа — через `change-management`». |

## Прочитать

1. Обязательно: `product.md` и `requirements.md` feature целиком; [glossary.md](../../../docs/product/glossary.md) — единственный источник имён; [data-model/](../../../docs/architecture/data-model/README.md) и все файлы сущностей в этой директории; [schemas/README.md](../../../schemas/README.md) — frontmatter. Правила — по AGENTS.md.
2. Если есть: `ui.md` feature; при изменении — текущий `model.md` полностью до правок.
3. Контекст: [business-rules.md](../../../docs/product/business-rules.md).

## Правила

Общие — AGENTS.md, `rules/ai-guardrails.md`. Ядро: текст документа, `title` и H1 — русский (заголовки секций — дословно по шаблону; ID, статусы, `TBD`/`ASSUMPTION` — английские); факт — без пометки, только из `product.md`, `requirements.md`, `docs/architecture/data-model/` или слов человека; неизвестное — `TBD: <что неизвестно>`; предположение — `ASSUMPTION: <текст>. Requires confirmation.`; своих ID у документа нет — только ссылки на FR/BR/NFR.

1. Сначала переиспользование: сущность уже есть в `docs/architecture/data-model/` — она идёт в «Существующие сущности» ссылкой и ролью в одну фразу.
2. Поля существующей сущности не копировать. Источник состава полей — файл сущности.
3. Новая сущность — только когда ни один файл в `docs/architecture/data-model/` не подходит. Совпадение по смыслу под другим именем — переиспользование.
4. Изменение существующей сущности — только дельта: `ADDED: <поле> — <тип> — <обязательность> — <зачем>`, `MODIFIED: <поле> — было <как> — стало <как> — <почему>`.
5. Удаление поля — через `change-management`; формы `REMOVED` в `model.md` нет.
6. Имена сущностей и полей — из `glossary.md`. Термина нет — `TBD` и предложить дополнить `glossary.md` отдельно.
7. Тип, обязательность, длина и формат поля — только подтверждённые; иначе `TBD` в ячейке. «По аналогии» значения не выводить.
8. Физическая схема — таблицы, индексы, миграции, выбор хранилища — в `technical.md`, сюда не писать.
9. Файлы в `docs/architecture/data-model/` этот skill не создаёт и не правит: промоут делает `feature-apply` после `approved`.
10. Сущности ID не получают (`schemas/README.md`); идентификатор сущности — имя её файла в kebab-case.
11. Трассируемость: каждая новая сущность и каждое изменение — минимум одна связь с FR или BR. Связи нет — `TBD` и вопрос человеку.
12. Новый документ — `type: model`, `status: draft`, `feature: <feature-name>`; `version`: MINOR без изменения состава сущностей, MAJOR при добавлении или изменении сущности; `approved` после правки → `review`.

## Шаги

1. Прочитать `product.md` и `requirements.md`; выписать данные, которые упоминают FR и BR.
2. Сопоставить каждый выписанный объект с файлами `docs/architecture/data-model/`: совпадение — переиспользование, иначе кандидат в новые (правила 1–3).
3. Если состав сущностей не выводится: задать до пяти вопросов одним списком и остановиться.
4. Создать `model.md` из [templates/model.md](../../../templates/model.md): все секции, неприменимые — `Not applicable: <причина>`; комментарии `<!-- AI: -->` выполнить и удалить.
5. Заполнить три секции сущностей: существующие — ссылками, новые — таблицами полей, изменения — дельтой (правила 4–7).
6. Диаграмма — Mermaid `erDiagram` в блоке `mermaid`; одна сущность без связей — `Not applicable: <причина>`. Заполнить «Трассируемость» (правило 11).
7. Добавить строку `model.md` в таблицу Documents файла `README.md` feature.
8. Запустить `node scripts/validate-docs.mjs`; добиться exit 0.

## Примеры

Неправильно — поля существующей сущности скопированы в feature, тип выдуман:

```text
### Пользователь
| Поле | Тип | Обязательность | Описание |
| email | string(255) | да | Адрес электронной почты |
```

Правильно — ссылка на файл сущности, дельта, неподтверждённый тип помечен:

```text
Существующие сущности: Пользователь (ссылка на файл сущности) — владелец учётной записи.
Изменения: ADDED: reset_token — TBD — TBD — хранит сессию восстановления.
```

## Чеклист

- [ ] Каждая существующая сущность дана ссылкой на файл в `docs/architecture/data-model/`, без копии полей.
- [ ] Новая сущность заведена только там, где подходящего файла нет.
- [ ] Имена сущностей и полей — из `glossary.md`; отсутствующий термин помечен `TBD`.
- [ ] Тип и обязательность каждого поля подтверждены или `TBD`; выдуманных значений нет.
- [ ] Изменения существующих сущностей — только `ADDED` и `MODIFIED`, без переописания сущности.
- [ ] Физической схемы БД, индексов и миграций в документе нет.
- [ ] Каждая секция шаблона заполнена или помечена `Not applicable: <причина>`.
- [ ] «Трассируемость» связывает каждую новую сущность и каждое изменение с FR или BR.
