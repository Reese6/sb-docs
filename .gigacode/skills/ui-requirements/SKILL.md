# Skill: ui-requirements

## Когда использовать

Создать или изменить `docs/features/<feature>/ui.md` — как интерфейс реализует требования: что пользователь делает, что видит в ответ, что происходит в каждом состоянии. Поведение первично: спецификация без дизайна возможна, дизайн без поведения — нет. Поводы: готовы `product.md` и `requirements.md`; добавить или изменить UI-требование; стадия UI оркестратора. Остальные документы — другие skills (AGENTS.md, «Как определить нужный skill»).

## Вход и стоп-условия

| Проверка | Если не выполнено |
|----------|-------------------|
| `product.md` и `requirements.md` feature существуют | Стоп. Ответ: «Сначала product.md (skill `product-documentation`) и requirements.md (skill `requirements`)». |
| Документ не `approved`, либо правка MINOR, либо apply утверждённого change proposal | Стоп. Ответ: «Содержательное изменение approved-документа — через `change-management`». |

## Прочитать

1. Обязательно: `product.md` и `requirements.md` feature целиком; [schemas/README.md](../../../schemas/README.md) — ID и frontmatter. Правила — по AGENTS.md.
2. Если есть: текущий `ui.md` целиком, включая deprecated (они занимают номера); `api/` и `technical.md` — валидация и ошибки в UI обязаны совпадать с контрактом API; существующая дизайн-система.
3. Глобальный контекст: [glossary.md](../../../docs/product/glossary.md) — термины интерфейса; [docs/api/errors.md](../../../docs/api/errors.md) — семантика ошибок.

## Правила

Общие — AGENTS.md, `rules/ai-guardrails.md`. Ядро: текст документа, `title` и H1 — русский (заголовки секций — дословно по шаблону; ID, статусы, `TBD`/`ASSUMPTION` — английские); факт — без пометки, только из `product.md`, `requirements.md`, существующей дизайн-системы или слов человека; неизвестное — `TBD: <что неизвестно>`; предположение — `ASSUMPTION: <текст>. Requires confirmation.`; существующие ID не менять и не переиспользовать.

1. Охват — FR/BR/NFR с ответом «как пользователь это делает или видит?». Чисто серверные требования в `ui.md` не попадают.
2. Каждый сценарий `product.md`, затрагивающий пользователя, проходим через описанные экраны и действия. Непроходимый — пробел: `TBD` в соответствующей секции.
3. Каждое действие — связка «пользователь делает X → система показывает или делает Y» со ссылкой на FR. «Экран содержит кнопку X» без реакции — неполное требование.
4. Определение требования — строго `- UI-004 (→ FR-012): <специфика UI>`: только ID источника и специфика уровня UI, формулировку FR/BR/NFR не копировать. Связи нет — найти источник или явно написать, почему её нет.
5. Новый ID = наибольший `UI-XXX` в feature (включая deprecated) + 1; пропуски не заполнять. Изменение формулировки сохраняет ID; удаление = пометка `deprecated`.
6. Состояния компонентов — только применимые (default, hover, focus, active, disabled, loading, success, error, empty): что видит пользователь, что доступно, условие перехода. У статического текста нет `loading`; заглушек нет.
7. Edge cases — только из `product.md` и `requirements.md` (повторная отправка, потеря сети, истечение срока, параллельные действия); фиксируются в Actions и Error states. Новые — предлагать пользователю, не вписывать как факт.
8. Валидация и ошибки совпадают с `requirements.md` и `api/`; коды и семантика — из `api/` и `docs/api/errors.md`. Расхождение — пометить конфликт, молча не «чинить».
9. Дизайн-систему не выдумывать: есть — ссылаться на её компоненты и токены; нет — описывать функционально («поле ввода кода», «кнопка отправки») без названий, цветов, отступов, шрифтов. Макеты — `TBD` со ссылкой на задачу дизайна; брейкпоинты — из дизайн-системы или `TBD`.
10. Тексты интерфейса, не заданные в источниках, — `TBD: текст` или `ASSUMPTION`. Слова «быстро», «удобно», «интуитивно», «корректно» — заменить наблюдаемым поведением (`rules/writing.md`).
11. Analytics events — только если аналитика требуется `product.md` или `requirements.md`; иначе `Not applicable`. События не выдумывать.
12. Новый документ — `type: ui`, `status: draft`. Существующий — минимальная правка; `version`: MINOR без изменения смысла, MAJOR при новых или изменённых UI-XXX; `approved` после правки → `review`.

## Шаги

1. Из `requirements.md` выбрать требования с интерфейсным проявлением (правило 1); проверить проходимость сценариев (правило 2).
2. Описать entry points (экраны, deep links, уведомления), экраны, компоненты, действия с реакцией (правило 3), навигацию («назад», выход из сценария, сохранение состояния), edge cases (правило 7).
3. Присвоить `UI-XXX` каждому существенному требованию (правила 4–5).
4. Описать состояния (правило 6), валидацию (правило, момент — ввод/blur/submit, текст ошибки), loading, empty, error states (сеть, сервер, бизнес-ошибки; возможен ли повтор), responsive, accessibility (клавиатура, фокус, screen reader, контраст) — применимо к этой feature, без пересказа общих стандартов.
5. Новый документ — из [templates/ui.md](../../../templates/ui.md): каждая секция заполнена или `Not applicable: <причина>`; комментарии `<!-- AI: -->` выполнить и удалить.
6. Заполнить Traceability: строка на каждый `UI-XXX`, включая deprecated, с минимум одной связью; затем обновить колонку «Покрыто (UI / API / technical)» в Traceability `requirements.md` (часть UI).
7. Если изменён существующий `UI-XXX`: `grep -rn "UI-004" docs/` → проверить расхождение с `requirements.md` и `api/` → конфликт пометить `TBD`/`ASSUMPTION` → обновить Traceability затронутых документов. Связанные документы молча не переписывать.
8. Запустить `node scripts/validate-docs.mjs`; добиться exit 0.

## Примеры

Неправильно — скопирована формулировка BR, выдумано число, нет ссылки на источник:

```text
- UI-005: Пользователь может запросить код повторно не чаще одного раза в 60 секунд, кнопка «Отправить снова» заблокирована 60 секунд.
```

Правильно — только ID источника и специфика UI:

```text
- UI-005 (→ BR-002): кнопка «Отправить снова» заблокирована до истечения интервала повторной отправки; рядом отображается оставшееся время.
```

## Чеклист

- [ ] Каждое существенное UI-требование имеет `UI-XXX` в форме `- UI-XXX (→ FR-XXX): …` либо явно помечено как несвязанное с причиной; номера не переиспользованы.
- [ ] У каждого действия зафиксирована реакция системы; каждый сценарий `product.md` проходим.
- [ ] Формулировки FR/BR/NFR не скопированы; каждая секция шаблона заполнена или помечена `Not applicable: <причина>`.
- [ ] Состояния описаны только там, где применимы; заглушек нет.
- [ ] Валидация и ошибки совпадают с `requirements.md` и `api/`; коды не выдуманы.
- [ ] Дизайн-система, макеты, тексты, брейкпоинты — из источников либо `TBD`/`ASSUMPTION`.
- [ ] Каждый `ASSUMPTION` — с `Requires confirmation.`; ни один не записан как факт.
- [ ] Traceability содержит все `UI-XXX`; колонка «Покрыто» в `requirements.md` обновлена.

Следующий шаг: .gigacode/skills/api-requirements, затем .gigacode/skills/technical-documentation и .gigacode/skills/documentation-review
