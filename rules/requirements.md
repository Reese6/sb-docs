# Requirements rules

Правила качества требований. Применяются к FR, BR, NFR, UI, API.

## Типы

```text
Functional Requirement  (FR)   что система делает
Business Rule           (BR)   правило предметной области
Non-functional Req.     (NFR)  измеримое качество (производительность, надёжность, безопасность)
Constraint                     внешнее ограничение (закон, платформа, legacy)
Acceptance Criterion           проверяемое условие приёмки
```

Не смешивать: constraint — не требование к поведению; acceptance criterion — не самостоятельное требование, а способ его проверки.

## Качество требования

Каждое требование обязано быть:

- **атомарным** — один пункт = одно требование; никаких «и/или, а также» с независимыми требованиями внутри;
- **однозначным** — единственная интерпретация; без неизмеримых слов (см. [writing.md](writing.md));
- **проверяемым** — можно написать тест или проверку, подтверждающую выполнение;
- **со стабильным ID** — формат и жизненный цикл ID — `schemas/README.md`.

Неправильно (не атомарно, не проверяемо):

```text
FR-005: Пользователь может запросить код по SMS, ввести его, и система должна работать быстро.
```

Правильно:

```text
FR-005: Пользователь может запросить код подтверждения на свой номер телефона.
FR-006: Пользователь может подтвердить операцию вводом полученного кода.
NFR-003: Код подтверждения доставляется в течение 30 секунд (TBD: подтвердить SLA провайдера).
```

## Формат записи

```text
FR-XXX: <формулировка в активном залоге: кто + может/должен + что>.
```

- Формулировка — законченное предложение, понятное без контекста соседних пунктов.
- Rationale (зачем) — отдельной строкой, если неочевидно.
- Условия и исключения — частью формулировки, не сноской.

## Acceptance Criteria

- Пригодны для прямого использования тестировщиком.
- Формат Given/When/Then, где применимо:

```text
Given пользователь запросил код подтверждения
When он вводит корректный код в пределах срока действия
Then операция подтверждается
```

- Каждый criterion ссылается на проверяемые FR/BR.

## Изменение требований

- Изменение формулировки не меняет ID.
- Требование не удаляется физически — помечается deprecated (ID навсегда занят).
- При изменении — найти связанные UI/API/technical требования и обновить их или пометить конфликт (процесс — `rules/ai-guardrails.md`).
