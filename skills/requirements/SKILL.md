# Skill: requirements

Создаёт и изменяет `docs/features/<feature-name>/requirements.md` — формальные требования feature.

Requirements формализуют ожидаемое поведение из `product.md` в атомарные, однозначные, проверяемые пункты со стабильными ID. Они не выбирают технологии (HOW) и не пересказывают продуктовый контекст (WHAT + WHY) — только формализуют его.

## Когда использовать

- `product.md` feature готов, нужно формализовать его в FR/BR/NFR и acceptance criteria.
- Пользователь просит добавить, изменить или пометить deprecated требование существующей feature.
- Orchestrator запускает стадию requirements после product documentation.

## Когда не использовать

| Задача | Правильный skill |
|--------|------------------|
| Описать проблему, пользователей, сценарии, scope | `skills/product-documentation` |
| Описать поведение интерфейса | `skills/ui-requirements` |
| Описать контракт API | `skills/api-requirements` |
| Описать техническое решение | `skills/technical-documentation` |
| Зафиксировать архитектурное решение | `skills/architecture-decisions` |
| Проверить существующую документацию | `skills/documentation-review` |
| Написать тест-кейсы ручного тестирования | `skills/test-cases` |

## Процесс

### Шаг 1. Прочитать контекст

До любых правок прочитать:

1. [rules/ai-guardrails.md](../../rules/ai-guardrails.md) — обязательный документ защиты от галлюцинаций; также [rules/requirements.md](../../rules/requirements.md), [rules/writing.md](../../rules/writing.md), [rules/linking.md](../../rules/linking.md), [rules/terminology.md](../../rules/terminology.md).
2. Стандарт ID и frontmatter: [schemas/README.md](../../schemas/README.md), структура записи требования — [schemas/requirement.schema.yaml](../../schemas/requirement.schema.yaml).
3. `product.md` данной feature — целиком. Это основной источник. Если `product.md` отсутствует — остановиться и направить пользователя в `skills/product-documentation`; требования без продуктовой постановки не пишутся.
4. Существующий `requirements.md` feature (если есть) — целиком, включая deprecated-требования: они занимают номера ID.
5. Глобальный контекст: [docs/product/business-rules.md](../../docs/product/business-rules.md), [docs/product/non-functional-requirements.md](../../docs/product/non-functional-requirements.md), [docs/product/glossary.md](../../docs/product/glossary.md) — чтобы ссылаться на существующие BR/NFR, а не дублировать их.
6. Остальные документы feature (`ui.md`, `api.md`, `technical.md`), если есть, — изменение требований может их затронуть.

### Шаг 2. Различать пять типов требований

Каждый пункт относится ровно к одному типу (полные правила — [rules/requirements.md](../../rules/requirements.md)):

| Тип | ID | Критерий различения |
|-----|----|---------------------|
| Functional Requirement | `FR-XXX` | Что делает система: наблюдаемое поведение «кто + может/должен + что». |
| Business Rule | `BR-XXX` | Правило предметной области; существует независимо от системы (лимиты, политики, регламенты бизнеса). |
| Non-functional Requirement | `NFR-XXX` | Измеримое качество: число или критерий (время ответа, доступность, безопасность). Без числа/критерия это не NFR. |
| Constraint | без ID | Внешнее ограничение (закон, платформа, legacy), которое требования обязаны учитывать; не описывает поведение системы. |
| Acceptance Criterion | без ID, ссылается на FR/BR | Проверяемое условие приёмки; способ проверки требования, а не самостоятельное требование. |

Тест для спорных случаев:

- Правило верно, даже если систему выключить, — `BR`, не `FR`.
- В формулировке нет измеримого критерия качества — это не `NFR`: либо найти критерий, либо `TBD` внутри формулировки.
- Пункт нельзя ни выполнить, ни нарушить поведением системы — это constraint, не требование.
- Пункт лишь проверяет другой пункт — это acceptance criterion, не отдельное требование.

### Шаг 3. Извлечь требования из product.md

- Источники требования: только `product.md`, глобальный контекст `docs/product/` и прямое указание человека. Придумывать требования запрещено ([rules/ai-guardrails.md](../../rules/ai-guardrails.md)).
- Каждый пункт Scope и каждый сценарий `product.md` — кандидат в один или несколько FR; правила предметной области — в BR; качества — в NFR.
- Формулировать в духе user story, но в форме требования: активный залог «кто + может/должен + что [при каких условиях]».
- Пункт scope, который не удаётся формализовать без выдумывания деталей, — записать с `TBD` внутри формулировки или вынести в Open Questions; не заполнять правдоподобным значением.
- Неизвестные лимиты, тайм-ауты, форматы — `TBD`; предположение — `ASSUMPTION: ... Requires confirmation.` Ни то, ни другое не записывается как факт.

### Шаг 4. Обеспечить качество каждого требования

По [rules/requirements.md](../../rules/requirements.md) каждое требование обязано быть:

- **атомарным** — один пункт = одно требование; «и/или», «а также» между независимыми требованиями — признак нарушения: разделить на отдельные ID;
- **однозначным** — единственная интерпретация, понятная без контекста соседних пунктов;
- **проверяемым** — можно написать тест или проверку, подтверждающую выполнение;
- **со стабильным ID** — формат и жизненный цикл — [schemas/README.md](../../schemas/README.md).

Слова из чёрного списка неизмеримых формулировок ([rules/writing.md](../../rules/writing.md)) без измеримого определения запрещены; пример правильной замены — там же.

### Шаг 5. Присвоить стабильные ID

По стандарту [schemas/README.md](../../schemas/README.md):

- Новый ID: следующий свободный номер данного типа в данной feature, **включая deprecated**; пропуски не заполняются.
- Изменение формулировки не меняет ID; требования не перенумеровываются при реорганизации документа.
- Требование не удаляется физически — помечается `deprecated` с причиной и заменяющим ID; deprecated ID не переиспользуются.
- Глобальные BR/NFR не копировать в feature — ссылаться по ID на [docs/product/business-rules.md](../../docs/product/business-rules.md) и [docs/product/non-functional-requirements.md](../../docs/product/non-functional-requirements.md) ([rules/linking.md](../../rules/linking.md)); одно требование живёт ровно в одном файле.

### Шаг 6. Написать Acceptance Criteria

- Каждый criterion пригоден для прямого использования тестировщиком: конкретные условия и наблюдаемый результат, без доуточнений «что имелось в виду».
- Формат Given/When/Then, где применим:

```text
AC для FR-001:
Given пользователь запросил код подтверждения
When он вводит корректный код в пределах срока действия
Then операция подтверждается
```

- Каждый criterion ссылается на проверяемые FR/BR; criterion без ссылки — висячий, ошибка.
- Без деталей интерфейса (экраны, кнопки) — это уровень `ui.md`; criterion описывает поведение, наблюдаемое извне.
- Покрыть и негативные пути, если они есть в сценариях `product.md`; не изобретать негативные сценарии, которых нет в постановке, — предлагать их в Open Questions.

### Шаг 7. Создать или изменить requirements.md

- Новый документ создавать строго по [templates/requirements.md](../../templates/requirements.md), включая все секции (Context, Functional Requirements, Business Rules, Non-functional Requirements, Constraints, Acceptance Criteria, Dependencies, Open Questions, Traceability) и YAML frontmatter.
- Неприменимые секции помечать «Not applicable: <причина>», не удалять и не заполнять заглушками.
- Frontmatter — по [schemas/README.md](../../schemas/README.md): `type: requirements`, новый документ — `status: draft`; `approved` выставляет только человек.
- Context — 2–3 предложения со ссылкой на `product.md`, без его пересказа.
- При изменении существующего документа — правило минимального изменения и повышение `version`/`status` по [CONTRIBUTING.md](../../CONTRIBUTING.md) и [schemas/README.md](../../schemas/README.md).

### Шаг 8. Заполнить Traceability

- Сводная таблица по всем ID feature:

```text
| ID | Источник (product-сценарий / BR) | Покрыто (UI / API / technical) |
```

- Источник — сценарий или пункт scope из `product.md`, либо BR, из которого требование следует.
- Колонка «Покрыто» заполняется по мере появления `ui.md`/`api.md`/`technical.md`; для новой feature она пуста — это нормальный вход для review, не ошибка.
- Каждое требование документа присутствует в таблице, включая deprecated.

### Шаг 9. При изменении существующих требований — impact-анализ

По [rules/linking.md](../../rules/linking.md) и [rules/ai-guardrails.md](../../rules/ai-guardrails.md):

1. Найти все документы, ссылающиеся на изменяемый ID (grep по `FR-XXX` и т.п.).
2. Определить затронутые UI/API/technical требования.
3. Обновить их или явно пометить конфликт (`TBD`/`ASSUMPTION`) — не переписывать связанные документы молча.
4. Обновить Traceability во всех затронутых документах.

### Шаг 10. Проверить результат

Перед завершением пройти чеклист:

- [ ] Все секции шаблона присутствуют; неприменимые помечены «Not applicable: <причина>»; незаполнимые содержат `TBD`, а не выдуманный текст.
- [ ] Каждый пункт отнесён ровно к одному из пяти типов; constraints не записаны как FR, acceptance criteria не выданы за требования.
- [ ] Каждое требование атомарно, однозначно, проверяемо; ни одного «и/или» с независимыми требованиями внутри пункта.
- [ ] ID соответствуют `^(FR|BR|NFR)-\d{3,}$`, номера не переиспользованы (проверено включая deprecated).
- [ ] Слова из чёрного списка отсутствуют либо сопровождаются измеримым определением.
- [ ] Каждый acceptance criterion ссылается на FR/BR и пригоден тестировщику напрямую.
- [ ] Каждое требование прослеживается к источнику в `product.md` / глобальном контексте / указании человека; выдуманных требований нет.
- [ ] Ни один `ASSUMPTION` не записан как факт; у каждого есть `Requires confirmation.`
- [ ] Глобальные BR/NFR не скопированы — только ссылки по ID.
- [ ] Traceability заполнена для всех ID документа.
- [ ] Frontmatter валиден по [schemas/README.md](../../schemas/README.md).

Завершая работу, сообщить пользователю: созданные/изменённые файлы, список `ASSUMPTION` (ждут подтверждения) и `TBD` (ждут ответа), непокрытые acceptance criteria пункты, рекомендуемый следующий шаг (обычно `skills/ui-requirements` и/или `skills/api-requirements`, затем `skills/documentation-review`).
