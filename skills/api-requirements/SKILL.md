# Skill: api-requirements

Создаёт и изменяет `docs/features/<feature-name>/api.md` — человекочитаемую спецификацию API feature.

Документ — контракт для людей: продакта, тестировщика, разработчика клиента и сервера. Источник контракта — `requirements.md`, а не воображение. **Документ не превращается в OpenAPI автоматически**: машиночитаемая спецификация создаётся только по явному запросу пользователя и отдельно от `api.md`.

## Когда использовать

- `product.md` и `requirements.md` feature готовы, нужно описать контракт API.
- Пользователь просит добавить или изменить API-требование существующей feature.
- Orchestrator запускает стадию API после requirements.

## Когда не использовать

| Задача | Правильный skill |
|--------|------------------|
| Описать проблему, пользователей, сценарии, scope | `skills/product-documentation` |
| Формализовать требования (FR/BR/NFR) | `skills/requirements` |
| Описать поведение интерфейса | `skills/ui-requirements` |
| Описать техническое решение | `skills/technical-documentation` |
| Зафиксировать архитектурное решение | `skills/architecture-decisions` |
| Проверить существующую документацию | `skills/documentation-review` |

## Процесс

### Шаг 1. Прочитать контекст

До любых правок прочитать:

1. [rules/ai-guardrails.md](../../rules/ai-guardrails.md) — обязательный документ защиты от галлюцинаций; также [rules/writing.md](../../rules/writing.md), [rules/linking.md](../../rules/linking.md), [rules/terminology.md](../../rules/terminology.md).
2. Стандарт ID и frontmatter: [schemas/README.md](../../schemas/README.md).
3. `product.md` и `requirements.md` данной feature — целиком. Это входные документы skill. Если какой-то из них отсутствует — остановиться и направить пользователя в `skills/product-documentation` или `skills/requirements`; контракт API без постановки и требований не описывается.
4. Существующий `api.md` feature (если есть) — целиком, включая deprecated-требования: они занимают номера ID.
5. Глобальные соглашения API: [docs/api/overview.md](../../docs/api/overview.md), [docs/api/conventions.md](../../docs/api/conventions.md), [docs/api/authentication.md](../../docs/api/authentication.md), [docs/api/errors.md](../../docs/api/errors.md) — контракт feature обязан им следовать.
6. `ui.md` и `technical.md` feature, если есть, — валидация и семантика ошибок в API обязаны совпадать с описанными в UI.

### Шаг 2. Определить охват API

Из `requirements.md` выбрать FR/BR/NFR, которые требуют взаимодействия клиента с сервером: у каждого спросить «какой запрос и ответ это реализует?». Требования без серверного проявления (чисто интерфейсные) в `api.md` не попадают.

- Источники контракта: `requirements.md`, глобальные `docs/api/`, существующие сервисы ([docs/api/services/](../../docs/api/services/README.md)) и прямое указание человека. Придумывать endpoints, поля и коды «по аналогии» запрещено ([rules/ai-guardrails.md](../../rules/ai-guardrails.md)).
- Каждый сценарий `product.md`, требующий сервера, обязан быть проходим через описанные endpoints; непроходимый сценарий — пробел контракта, зафиксировать `TBD` или вопрос в Open Questions.

### Шаг 3. Держать контракт человекочитаемым

- `api.md` — проза, таблицы и примеры, понятные без инструментов; не YAML-дамп.
- Не превращать документ в OpenAPI, если это не требуется: генерация OpenAPI — отдельная задача по явному запросу, `api.md` остаётся источником смысла (назначение, правила, побочные эффекты), который в схему не помещается.

### Шаг 4. Описать каждый endpoint — 16 аспектов

Для каждого endpoint (метод, путь, `API-XXX`) проверить каждый аспект; неприменимый — пометить в соответствующей секции «Not applicable: <причина>», не молчать:

| Аспект | Что зафиксировать |
|--------|-------------------|
| Назначение | Зачем endpoint существует, какие требования реализует. |
| Request | Параметры пути/query, заголовки, тело: поле — тип — обязательность — описание. |
| Response | Успешный статус-код и тело: поле — тип — описание. |
| Validation | Серверные правила валидации и ошибка при нарушении; совпадение с клиентской валидацией `ui.md`. |
| Authentication | Требуется ли аутентификация; специфика endpoint (например, анонимный доступ). |
| Authorization | Требуемые права/роли/scope; кто не может вызывать. |
| Errors | Специфичные ошибки endpoint: статус, code, условие возникновения. |
| Idempotency | Идемпотентность мутирующих операций: механизм, семантика повтора. |
| Concurrency | Поведение при конкурентных запросах (описывается в секции Idempotency, если значимо). |
| Pagination | Для списочных endpoints: лимиты по умолчанию, максимум. |
| Filtering | Доступные фильтры: параметр — тип — семантика. |
| Sorting | Доступные поля сортировки и порядок по умолчанию. |
| Rate limiting | Лимиты частоты вызовов и поведение при превышении. |
| Security | Специфичные риски и меры: чувствительные данные, защита от перебора, маскирование. |
| Side effects | Что меняется помимо ответа: записи, отправка SMS/email, списание средств. |
| Events | Публикуемые события: топик, схема, момент публикации. |

Несколько endpoints — подраздел на каждый; секции заполнять per-endpoint, если контракты различаются.

### Шаг 5. Не дублировать глобальные `docs/api/`

- Механизм аутентификации, формат ошибок, общие коды, схема пагинации и форматы данных описаны **один раз** в `docs/api/` — в feature только ссылка и специфика endpoint.
- Специфичный для endpoint код ошибки — в `api.md` feature со ссылкой на общий формат [docs/api/errors.md](../../docs/api/errors.md); новый общий код — предложить в `docs/api/errors.md`, не заводить локально.
- Endpoint, нарушающий конвенцию [docs/api/conventions.md](../../docs/api/conventions.md), обязан иметь явное обоснование (ADR или пометка в `api.md`); молча отклоняться нельзя.

### Шаг 6. Присвоить API-XXX и связать с требованиями

По стандарту [schemas/README.md](../../schemas/README.md):

- Каждое существенное API-требование получает `API-XXX`: следующий свободный номер в данной feature, **включая deprecated**; пропуски не заполняются.
- Каждый `API-XXX` ссылается на `FR-XXX`, `BR-XXX` или `NFR-XXX`: `API-007 (→ FR-012): ...` или `Trace: FR-012`. Направление ссылки — от API к источнику ([rules/linking.md](../../rules/linking.md)). API-требование без связи — кандидат в висячие; либо найти источник, либо явно пометить, почему связи нет.
- Формулировки FR/BR/NFR не копировать — только ID и специфика уровня API:

Неправильно: «Пользователь может запросить код повторно не чаще одного раза в 60 секунд, при более частом вызове endpoint возвращает 429».
Правильно: «API-003: повторный вызов ранее истечения интервала повтора возвращает 429 (BR-002)».

- Изменение формулировки не меняет ID; требование не удаляется физически — помечается `deprecated`; deprecated ID не переиспользуются.

### Шаг 7. Не выдумывать контракт

- Неизвестные endpoints, поля, коды ошибок, лимиты, тайм-ауты, форматы — `TBD`; предположение — `ASSUMPTION: ... Requires confirmation.` Ни то, ни другое не записывается как факт ([rules/ai-guardrails.md](../../rules/ai-guardrails.md)).
- Признак нарушения: в документе появилось конкретное значение (число, формат, код), которого нет ни в `requirements.md`, ни в `docs/api/`, и которое не дал человек.
- Значения в Examples — правдоподобные, но явно тестовые; реальные данные не использовать.

### Шаг 8. Создать или изменить api.md

- Новый документ создавать строго по [templates/api.md](../../templates/api.md), включая все секции (Purpose, Related requirements, Endpoint, Authentication, Authorization, Request, Validation, Response, Errors, Pagination, Filtering, Sorting, Idempotency, Rate limits, Security, Side effects, Events, Examples, Traceability) и YAML frontmatter.
- Неприменимые секции помечать «Not applicable: <причина>», не удалять.
- Frontmatter — по [schemas/README.md](../../schemas/README.md): `type: api`, новый документ — `status: draft`; `approved` выставляет только человек.
- При изменении существующего документа — правило минимального изменения (`CONTRIBUTING.md`): менять только нужное; изменение `approved`-документа переводит его в `review`; `version`: MINOR — правки без изменения смысла, MAJOR — изменение/добавление требований.

### Шаг 9. Заполнить Traceability

- Сводная таблица по всем `API-XXX` документа:

```text
| API ID | Требование | Endpoint |
```

- Каждый `API-XXX` присутствует в таблице, включая deprecated; минимум одна связь с FR/BR/NFR — висячие находит review.
- После заполнения — обновить колонку «Покрыто (API)» в Traceability `requirements.md` данной feature.

### Шаг 10. При изменении существующих API-требований — impact-анализ

По [rules/linking.md](../../rules/linking.md) и [rules/ai-guardrails.md](../../rules/ai-guardrails.md):

1. Найти все документы, ссылающиеся на изменяемый `API-XXX` (grep по ID).
2. Проверить, не разошёлся ли контракт с `requirements.md` и `ui.md` (валидация, семантика ошибок); конфликт — пометить `TBD`/`ASSUMPTION`, не переписывать связанные документы молча.
3. Обновить Traceability во всех затронутых документах.

### Шаг 11. Проверить результат

Перед завершением пройти чеклист:

- [ ] Все секции шаблона присутствуют; неприменимые помечены «Not applicable: <причина>»; незаполнимые содержат `TBD`, а не выдуманный текст.
- [ ] Все 16 аспектов (назначение, request, response, validation, authentication, authorization, errors, idempotency, concurrency, pagination, filtering, sorting, rate limiting, security, side effects, events) покрыты или помечены «Not applicable».
- [ ] Документ человекочитаем; в OpenAPI не превращён без явного запроса.
- [ ] Каждое существенное API-требование имеет `API-XXX`; ID соответствуют `^API-\d{3,}$`, номера не переиспользованы (проверено включая deprecated).
- [ ] Каждый `API-XXX` ссылается на FR/BR/NFR либо явно помечен как несвязанный с причиной.
- [ ] Формулировки FR/BR/NFR не скопированы — только ID и специфика API.
- [ ] Глобальные соглашения (auth, ошибки, пагинация, форматы) не скопированы — только ссылки на `docs/api/` и специфика endpoint.
- [ ] Ни одного выдуманного endpoint, поля, кода или лимита; каждое конкретное значение прослеживается к `requirements.md`, `docs/api/` или указанию человека.
- [ ] Ни один `ASSUMPTION` не записан как факт; у каждого есть `Requires confirmation.`
- [ ] Значения в Examples — тестовые, не реальные.
- [ ] Traceability заполнена для всех `API-XXX`; Traceability `requirements.md` обновлена.
- [ ] Frontmatter валиден по [schemas/README.md](../../schemas/README.md).

Завершая работу, сообщить пользователю: созданные/изменённые файлы, список `ASSUMPTION` (ждут подтверждения) и `TBD` (ждут ответа), FR/BR/NFR без API-покрытия, рекомендуемый следующий шаг (обычно `skills/technical-documentation`, затем `skills/documentation-review`).
