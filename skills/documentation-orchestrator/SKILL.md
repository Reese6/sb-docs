# Skill: documentation-orchestrator

Координирует полный цикл документирования feature в `docs/features/<feature-name>/`. Сам не пишет и не проверяет ни один документ — содержательную работу выполняют семь специализированных skills. Задача оркестратора — определить правильный набор стадий и провести их в правильном порядке.

Базовый pipeline:

```text
User request
    ↓
Read product context
    ↓
Identify feature
    ↓
Product documentation
    ↓
Requirements
    ↓
┌───────────────┐
│               │
UI             API
│               │
└───────┬───────┘
        ↓
Technical documentation
        ↓
ADR if required
        ↓
Documentation review
```

Стадии «Read product context» и «Identify feature» выполняет сам оркестратор (шаги 1 и 3 процесса); остальные стадии — специализированные skills.

Ключевое правило: pipeline — максимальный маршрут, а не обязательный. Запускаются только стадии, необходимые для запроса: изменение текста кнопки не должно порождать ADR и technical specification. Единственная непропускаемая стадия при любых изменениях — documentation review.

## Когда использовать

- Пользователь просит задокументировать новую feature целиком — от постановки до технического решения.
- Запрос затрагивает несколько типов документов сразу (например, изменение scope, тянущее requirements, UI и API).
- Пользователь описывает намерение, не называя конкретный документ, и состав нужных документов неочевиден.

## Когда не использовать

Запрос, укладывающийся в один документ, оркестратора не требует — идти напрямую:

| Задача | Правильный skill |
|--------|------------------|
| Описать проблему, пользователей, сценарии, scope | `skills/product-documentation` |
| Формализовать требования (FR/BR/NFR) | `skills/requirements` |
| Описать поведение интерфейса | `skills/ui-requirements` |
| Описать контракт API | `skills/api-requirements` |
| Описать техническое решение | `skills/technical-documentation` |
| Зафиксировать архитектурное решение | `skills/architecture-decisions` |
| Проверить существующую документацию | `skills/documentation-review` |

Писать и проверять документы — тоже не задача оркестратора: вся содержательная работа выполняется перечисленными skills по их собственным процессам.

## Процесс

Шаги 2–6 — планирование, шаги 7–8 — выполнение. Каждая стадия выполняется её специализированным skill по его собственному SKILL.md; оркестратор не воспроизводит, не сокращает и не подменяет эти процессы.

### Шаг 1. Прочитать контекст

До начала оркестрации прочитать:

1. [rules/ai-guardrails.md](../../rules/ai-guardrails.md) — обязательный документ защиты от галлюцинаций. Остальные правила здесь не читаются: каждый специализированный skill читает их сам на своей стадии.
2. Глобальный продуктовый контекст (стадия «Read product context»): [docs/product/overview.md](../../docs/product/overview.md) и [docs/product/glossary.md](../../docs/product/glossary.md) — понять продукт и термины запроса; остальные документы `docs/product/` читают стадии pipeline.
3. Структуру feature: [docs/features/README.md](../../docs/features/README.md) и [schemas/feature.schema.yaml](../../schemas/feature.schema.yaml) — какие документы обязательны (`README.md`, `product.md`, `requirements.md`), какие опциональны (`ui.md`, `api.md`, `technical.md`, `decisions/`).
4. Статусы и frontmatter: [schemas/README.md](../../schemas/README.md) — понадобятся на шаге 5.

### Шаг 2. Понять намерение пользователя

- Определить, что пользователь хочет изменить в продукте, а не какой файл отредактировать; за формулировкой-решением восстановить задачу.
- Классифицировать масштаб: новая feature, изменение существующей, точечная правка одного аспекта, только проверка.
- Неясное намерение — спросить пользователя; не додумывать и не расширять запрос ([rules/ai-guardrails.md](../../rules/ai-guardrails.md)).
- Запрос уже сформулирован в терминах одного документа («поправь ui.md», «добавь FR») — оркестрация не нужна: направить напрямую по таблице «Когда не использовать».

### Шаг 3. Определить затрагиваемую feature

- Найти feature среди директорий `docs/features/` (имена — kebab-case).
- Feature нет — она новая: выбрать имя в kebab-case; директорию и `README.md` создаст стадия product documentation, не оркестратор.
- Неоднозначно, какая feature затронута, — спросить пользователя, не выбирать молча.
- Затронуто несколько features — согласовать с пользователем порядок; pipeline проходится для каждой feature отдельно.
- Запрос касается только глобальных документов (`docs/product/`, `docs/api/`, `docs/architecture/`) — это не feature-pipeline: глобальный ADR — в `skills/architecture-decisions`, остальное правится напрямую по `rules/`; сообщить об этом пользователю.

### Шаг 4. Определить необходимые стадии

Для каждой стадии pipeline проверить её критерий; критерий не выполнен — стадия не запускается:

| Стадия | Запускать, когда |
|--------|------------------|
| Product documentation | feature новая (нет `product.md`) или запрос меняет проблему, цель, пользователей, сценарии, scope (WHAT + WHY) |
| Requirements | создан или содержательно изменён `product.md`, либо запрос напрямую затрагивает FR/BR/NFR или acceptance criteria |
| UI | затронуто наблюдаемое поведение интерфейса; у backend-only feature стадия не запускается |
| API | затронут контракт клиент–сервер (endpoints, поля, ошибки); у feature без внешнего API стадия не запускается |
| Technical | затронута реализация: компоненты, данные, интеграции, миграции |
| ADR | есть кандидат — пометка в Alternatives `technical.md` или прямой запрос; заслуживает ли решение ADR, проверяет шаг «Проверить, заслуживает ли решение ADR» самого `skills/architecture-decisions`, не оркестратор |
| Review | всегда, когда изменён хотя бы один документ; единственная стадия, которую нельзя пропустить |

Стадия не запускается «на всякий случай», «для полноты» или потому, что опционального файла ещё нет: по [schemas/feature.schema.yaml](../../schemas/feature.schema.yaml) отсутствие `ui.md`, `api.md`, `technical.md` или `decisions/` — не пробел.

```text
Изменение текста кнопки    → UI → Review
Новая backend-only feature → Product → Requirements → API → Technical → Review
```

Сомнение, нужна ли стадия, — сверить намерение с секциями «Когда использовать» / «Когда не использовать» соответствующего skill: они первичны. Остающееся сомнение — вопрос пользователю, а не стадия «про запас».

### Шаг 5. Определить существующие документы

- Провести инвентаризацию `docs/features/<feature-name>/` по [schemas/feature.schema.yaml](../../schemas/feature.schema.yaml): какие файлы есть; у каждого — `status` и `version` из frontmatter ([schemas/README.md](../../schemas/README.md)).
- Документ есть — его стадия работает в режиме изменения; документа нет — в режиме создания по шаблону. Механика обоих режимов (минимальные правки, шаблоны, перевод `approved` в `review`, версии, impact-анализ) — внутри пишущих skills; оркестратор её не повторяет.
- Затрагиваются `approved`-документы — отметить это в плане (шаг 7): пользователь должен заранее знать, что утверждённые документы перейдут в `review`.
- Отсутствие обязательных `product.md` или `requirements.md` зафиксировать — это вход шага 6.
- На этом шаге оркестратор ничего не редактирует и статусы не меняет.

### Шаг 6. Определить зависимости

Порядок закреплён pipeline и «Порядком создания документов» в [docs/features/README.md](../../docs/features/README.md):

| Стадия | Требует |
|--------|---------|
| Product documentation | глобальный контекст `docs/product/` |
| Requirements | `product.md` |
| UI | `product.md`, `requirements.md` |
| API | `product.md`, `requirements.md` |
| Technical | `product.md`, `requirements.md`; `ui.md`/`api.md` — если есть |
| ADR | контекст решения, обычно `technical.md` |
| Review | завершение всех пишущих стадий |

- Вход нужной стадии отсутствует — добавить недостающую стадию перед ней: просят API при отсутствии `requirements.md` — сначала requirements; нет и `product.md` — сначала product. Специализированные skills сами останавливаются без входов — план оркестратора обязан исключать такие остановки заранее.
- Обратная зависимость: содержательное изменение верхнего документа включает в план пересмотр нижних (изменение scope в `product.md` — стадия requirements обязательна; UI/API — по охвату изменения). Механика impact-анализа — внутри пишущих skills; оркестратор лишь включает стадии в план.
- UI и API взаимно независимы: нужна любая из них, обе или ни одной; порядок между ними свободный, по умолчанию UI, затем API. Согласование валидации и семантики ошибок между `ui.md` и `api.md` выполняют сами skills.

### Шаг 7. Выбрать последовательность и запустить стадии

- Последовательность — стадии из шага 4 плюс недостающие входы из шагов 5–6, упорядоченные по pipeline; review всегда последняя.
- Сообщить план пользователю до запуска: стадии по порядку, для каждой — создание или изменение какого файла, затронутые `approved`-документы. Стадии, добавленные сверх явно запрошенного (недостающие входы, пересмотр нижних документов), подтвердить у пользователя; scope молча не расширять.
- Запускать стадии по очереди; каждая выполняется своим специализированным skill по его SKILL.md целиком, включая его чтение контекста и финальный чеклист.
- План может измениться по ходу: `skills/technical-documentation` пометил кандидата на ADR — добавить стадию `skills/architecture-decisions`; стадия остановилась (нет входа, ждёт подтверждения `ASSUMPTION`, не подключён код в `services/`) — остановиться и согласовать с пользователем, а не выдумывать ответы ради прохождения pipeline до конца.
- Собирать итоги каждой стадии: созданные и изменённые файлы, `ASSUMPTION`, `TBD` — понадобятся на шаге 9.

### Шаг 8. Запустить documentation review

- Изменён хотя бы один документ — запустить `skills/documentation-review`. Review обязателен после любых изменений, независимо от числа стадий и объёма правки — даже для одной строки в одном файле. Пропуск review — нарушение процесса.
- Scope review — затронутая feature (режим по умолчанию самого review).
- Изменений не было (работа остановилась на вопросах, план не выполнялся) — review не запускается: тот же принцип, что и для остальных стадий.
- Отчёт review передать пользователю целиком: ERROR/WARNING и четыре итоговых списка. Находки не устранять молча: устранение — решение человека, выполняют пишущие skills; после устранения — повторный review затронутого.

### Шаг 9. Проверить результат

Перед завершением пройти чеклист:

- [ ] Намерение понято и не расширено; неясности спрошены у пользователя, а не додуманы.
- [ ] Feature определена; для новой feature директорию создала стадия product documentation.
- [ ] Запущены только стадии, следующие из намерения; ни одной «на всякий случай» — правка текста кнопки не породила technical и ADR.
- [ ] Все стадии плана обеспечены входами; ни одна не остановилась из-за отсутствия входа, которое можно было предвидеть.
- [ ] Порядок стадий соответствует pipeline; UI/API запускались только при затронутых интерфейсе или контракте.
- [ ] Каждая стадия выполнена её специализированным skill; оркестратор сам не писал и не проверял документы.
- [ ] План и его изменения по ходу сообщены пользователю; расширения scope подтверждены.
- [ ] После изменений запущен `skills/documentation-review`; отчёт получен и передан пользователю полностью; находки не «исправлены» молча.
- [ ] Статусы не выставлены самовольно: новые документы — `draft`; `approved` выставляет только человек.
- [ ] Итоги всех стадий собраны: файлы, `ASSUMPTION`, `TBD`.

Завершая работу, сообщить пользователю: выполненные стадии и их порядок; созданные и изменённые файлы по стадиям; сводные списки `ASSUMPTION` (ждут подтверждения) и `TBD` (ждут ответа) со всех стадий; итог review (количество ERROR/WARNING и четыре итоговых списка); документы, ожидающие перевода в `approved` человеком; рекомендуемые следующие действия — устранение находок review соответствующими пишущими skills.
