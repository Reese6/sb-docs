# Skill: ui-requirements

Создаёт и изменяет `docs/features/<feature-name>/ui.md` — спецификацию интерфейса feature.

Приоритет — **поведение** интерфейса, а не только внешний вид: что пользователь делает, что видит в ответ, что происходит в каждом состоянии. Макеты и визуальный стиль вторичны; спецификация без дизайна возможна, дизайн без поведения — нет.

## Когда использовать

- `product.md` и `requirements.md` feature готовы, нужно описать интерфейс.
- Пользователь просит добавить или изменить UI-требование существующей feature.
- Orchestrator запускает стадию UI после requirements.

## Когда не использовать

| Задача | Правильный skill |
|--------|------------------|
| Описать проблему, пользователей, сценарии, scope | `skills/product-documentation` |
| Формализовать требования (FR/BR/NFR) | `skills/requirements` |
| Описать контракт API | `skills/api-requirements` |
| Описать техническое решение | `skills/technical-documentation` |
| Зафиксировать архитектурное решение | `skills/architecture-decisions` |
| Проверить существующую документацию | `skills/documentation-review` |

## Процесс

### Шаг 1. Прочитать контекст

До любых правок прочитать:

1. [rules/ai-guardrails.md](../../rules/ai-guardrails.md) — обязательный документ защиты от галлюцинаций; также [rules/writing.md](../../rules/writing.md), [rules/linking.md](../../rules/linking.md), [rules/terminology.md](../../rules/terminology.md).
2. Стандарт ID и frontmatter: [schemas/README.md](../../schemas/README.md).
3. `product.md` и `requirements.md` данной feature — целиком. Это входные документы skill. Если какой-то из них отсутствует — остановиться и направить пользователя в `skills/product-documentation` или `skills/requirements`; UI без постановки и требований не описывается.
4. Существующий `ui.md` feature (если есть) — целиком, включая deprecated-требования: они занимают номера ID.
5. Глобальный контекст: [docs/product/glossary.md](../../docs/product/glossary.md) — термины интерфейса называть по глоссарию.
6. `api.md` и `technical.md` feature, если есть, — валидация и семантика ошибок в UI обязаны совпадать с контрактом API.

### Шаг 2. Определить охват интерфейса

Из `requirements.md` выбрать FR/BR/NFR, которые видимы пользователю: у каждого спросить «как пользователь это делает или видит?». Требования без интерфейсного проявления (чисто серверные) в `ui.md` не попадают.

- Источники UI-требований: `product.md` (сценарии, пользователи), `requirements.md` (FR/BR/NFR), существующая дизайн-система и прямое указание человека. Придумывать экраны, потоки и элементы, не следующие из них, запрещено ([rules/ai-guardrails.md](../../rules/ai-guardrails.md)).
- Каждый сценарий `product.md`, затрагивающий пользователя, обязан быть проходим через описанные экраны и действия; непроходимый сценарий — пробел спецификации, зафиксировать `TBD` или вопрос в Open Questions.

### Шаг 3. Описать поведение, а не только вид

Для каждого экрана и компонента фиксировать связку «действие → реакция»:

- **Entry points** — откуда пользователь попадает в интерфейс (экраны, deep links, уведомления).
- **Actions** — «пользователь делает X → система показывает/делает Y»; каждое действие трассируется к FR.
- **Navigation** — переходы между экранами, поведение «назад», выход из сценария, сохранение состояния при переходах.
- **Edge cases** — граничные случаи из сценариев `product.md` и requirements: повторная отправка, потеря сети, истечение срока, параллельные действия. Не изобретать edge cases, которых нет в постановке, — предлагать их в Open Questions.

Формулировка «экран содержит кнопку X» без описания, что происходит при нажатии, — неполное требование.

### Шаг 4. Присвоить ID и связать с требованиями

По стандарту [schemas/README.md](../../schemas/README.md):

- Каждое существенное UI-требование получает `UI-XXX`: следующий свободный номер в данной feature, **включая deprecated**; пропуски не заполняются.
- По возможности каждый `UI-XXX` ссылается на `FR-XXX`, `BR-XXX` или `NFR-XXX`: `UI-004 (→ FR-012): ...` или `Trace: FR-012`. Направление ссылки — от UI к источнику ([rules/linking.md](../../rules/linking.md)). UI-требование без связи — кандидат в висячие; либо найти источник, либо явно пометить, почему связи нет.
- Формулировки FR/BR/NFR не копировать — только ID и специфика уровня UI:

Неправильно: «Пользователь может запросить код повторно не чаще одного раза в 60 секунд, кнопка "Отправить снова" заблокирована 60 секунд».
Правильно: «UI-005: кнопка "Отправить снова" заблокирована до истечения интервала повтора (BR-002)».

- Изменение формулировки не меняет ID; требование не удаляется физически — помечается `deprecated`; deprecated ID не переиспользуются.

### Шаг 5. Описать состояния компонентов

Для каждого значимого компонента описать состояния — **только те, которые к нему применимы**:

```text
default
hover
focus
active
disabled
loading
success
error
empty
```

- Для каждого применимого состояния — что видит пользователь и какие действия доступны.
- Неприменимые состояния не описывать и не заполнять заглушками: у статического текста нет `loading`, у кнопки нет `empty`.
- Условия переходов между состояниями — явно: когда кнопка становится `disabled`, когда форма переходит в `error`.

### Шаг 6. Покрыть обязательные аспекты

Проверить каждый аспект; неприменимый — пометить в соответствующей секции «Not applicable: <причина>», не молчать:

| Аспект | Что зафиксировать |
|--------|-------------------|
| Validation | Правило клиентской валидации, момент срабатывания (ввод / blur / submit), текст ошибки. Правила обязаны совпадать с `requirements.md` и `api.md`; расхождение — пометить конфликт, не «чинить» молча. |
| Loading | Что видит пользователь во время загрузки: скелетоны, спиннеры, блокировка повторной отправки. |
| Empty states | Поведение при отсутствии данных: текст, призыв к действию. |
| Error states | Поведение при ошибках сети, сервера, бизнес-ошибках: что показывается, возможен ли повтор. Семантика ошибок — из `api.md` и [docs/api/errors.md](../../docs/api/errors.md), не выдумывать коды. |
| Navigation | Переходы, «назад», выход из сценария. |
| Edge cases | Граничные случаи сценариев (шаг 3). |
| Responsive | Поведение на разных размерах экранов и платформах, если применимо. Брейкпоинты не выдумывать — из дизайн-системы или `TBD`. |
| Accessibility | Клавиатурная навигация, порядок фокуса, screen reader, контраст — применимо к этой feature; общие стандарты не пересказывать. |

### Шаг 7. Не выдумывать дизайн

- **Не придумывать дизайн-систему, если она отсутствует.** Есть существующая — ссылаться на её компоненты и токены; нет — описывать компоненты функционально («поле ввода кода», «кнопка отправки») без изобретения названий компонентов, цветов, отступов, шрифтов.
- Макеты не выдумывать: нет дизайна — `TBD` со ссылкой на задачу дизайна.
- Тексты интерфейса (ошибки, пустые состояния, подписи) не сочинять как финальные: не заданных в источниках — помечать `TBD: текст` или `ASSUMPTION: ... Requires confirmation.`
- Чёрный список слов без измеримого определения ([rules/writing.md](../../rules/writing.md)): «удобно», «быстро», «интуитивно» и подобные — заменить наблюдаемым поведением или измеримым критерием.

### Шаг 8. Создать или изменить ui.md

- Новый документ создавать строго по [templates/ui.md](../../templates/ui.md), включая все секции (Purpose, Related requirements, Entry points, Screens, Components, Component states, Actions, Validation, Loading states, Empty states, Error states, Navigation, Responsive behaviour, Accessibility, Analytics events, Traceability) и YAML frontmatter.
- Неприменимые секции помечать «Not applicable: <причина>», не удалять.
- Frontmatter — по [schemas/README.md](../../schemas/README.md): `type: ui`, новый документ — `status: draft`; `approved` выставляет только человек.
- Analytics events — только если аналитика требуется `product.md`/`requirements.md`; иначе «Not applicable». События не изобретать.
- При изменении существующего документа — правило минимального изменения (`CONTRIBUTING.md`): менять только нужное; изменение `approved`-документа переводит его в `review`; `version`: MINOR — правки без изменения смысла, MAJOR — изменение/добавление требований.

### Шаг 9. Заполнить Traceability

- Сводная таблица по всем `UI-XXX` документа:

```text
| UI ID | Требование | Экран/компонент |
```

- Каждый `UI-XXX` присутствует в таблице, включая deprecated; минимум одна связь с FR/BR/NFR — висячие находит review.
- После заполнения — обновить колонку «Покрыто (UI)» в Traceability `requirements.md` данной feature.

### Шаг 10. При изменении существующих UI-требований — impact-анализ

По [rules/linking.md](../../rules/linking.md) и [rules/ai-guardrails.md](../../rules/ai-guardrails.md):

1. Найти все документы, ссылающиеся на изменяемый `UI-XXX` (grep по ID).
2. Проверить, не разошёлся ли UI с `requirements.md` и `api.md`; конфликт — пометить `TBD`/`ASSUMPTION`, не переписывать связанные документы молча.
3. Обновить Traceability во всех затронутых документах.

### Шаг 11. Проверить результат

Перед завершением пройти чеклист:

- [ ] Все секции шаблона присутствуют; неприменимые помечены «Not applicable: <причина>»; незаполнимые содержат `TBD`, а не выдуманный текст.
- [ ] Каждое существенное UI-требование имеет `UI-XXX`; ID соответствуют `^UI-\d{3,}$`, номера не переиспользованы (проверено включая deprecated).
- [ ] Каждый `UI-XXX` ссылается на FR/BR/NFR либо явно помечен как несвязанный с причиной.
- [ ] Формулировки FR/BR/NFR не скопированы — только ID и специфика UI.
- [ ] Описано поведение: у каждого действия зафиксирована реакция системы; каждый пользовательский сценарий `product.md` проходим через описанные экраны.
- [ ] Состояния компонентов описаны только там, где применимы; заглушек для неприменимых состояний нет.
- [ ] Все 8 аспектов (validation, responsive, accessibility, navigation, edge cases, error states, empty states, loading) покрыты или помечены «Not applicable».
- [ ] Дизайн-система не выдумана; компоненты, цвета, брейкпоинты, тексты и коды ошибок — из источников либо `TBD`/`ASSUMPTION`.
- [ ] Ни один `ASSUMPTION` не записан как факт; у каждого есть `Requires confirmation.`
- [ ] Traceability заполнена для всех `UI-XXX`; Traceability `requirements.md` обновлена.
- [ ] Frontmatter валиден по [schemas/README.md](../../schemas/README.md).

Завершая работу, сообщить пользователю: созданные/изменённые файлы, список `ASSUMPTION` (ждут подтверждения) и `TBD` (ждут ответа, в том числе задачи дизайна), FR/BR/NFR без UI-покрытия, рекомендуемый следующий шаг (обычно `skills/api-requirements`, затем `skills/documentation-review`).
