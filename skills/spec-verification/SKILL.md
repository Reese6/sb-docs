# Skill: spec-verification

Сверяет документацию с исходным кодом в `services/` в обе стороны и формирует отчёт. Отчёт — единственный артефакт: skill **не создаёт, не изменяет и не «исправляет» ни один документ `docs/` и ни один файл в `services/`** — даже очевидную опечатку и даже когда расхождение выглядит однозначным.

Направление разрешения расхождений задано жёстко (`AGENTS.md`, раздел «Source of truth»; `services/README.md`): requirements — правда о **требуемом** поведении, код — правда о **текущей** реализации. Skill **никогда не предлагает переписать требование под код**. Каждое расхождение адресуется человеку с указанием, какой skill его устраняет.

Два прохода:

```text
Прямой  (spec → code)  каждое требование: реализовано? покрыто тестом?   пропуски
Обратный (code → spec) каждая наблюдаемая поверхность кода: описана?     дрейф
```

Проходы обязательны оба и не заменяют друг друга: они находят разное и **страхуют друг друга**. Противоречие, потерянное прямым проходом из-за неверного опровержения, обратный проход находит независимо — со стороны кода, где конкретное значение видно буквально.

## Когда использовать

- Код сервисов подключён в `services/`, и нужно узнать реальное покрытие требований реализацией.
- Перед переводом feature в `approved` — убедиться, что утверждается описание работающей системы, а не намерения.
- После крупного изменения кода — найти дрейф: что реализовано сверх спеки и что ей противоречит.
- Перед написанием или обновлением `technical.md` — собрать фактическую картину для секции `Current implementation`.
- Пользователь просит сверить документацию с кодом, проверить реализованность требований или найти недокументированное поведение.

## Когда не использовать

| Задача | Правильный skill |
|--------|------------------|
| Проверить документацию саму по себе: структура, качество требований, противоречия между документами, терминология | `skills/documentation-review` |
| Описать текущую реализацию в `technical.md` | `skills/technical-documentation` |
| Сформулировать или исправить требование | `skills/requirements` |
| Описать контракт API | `skills/api-requirements` |
| Описать поведение интерфейса | `skills/ui-requirements` |
| Зафиксировать архитектурное решение | `skills/architecture-decisions` |
| Содержательно изменить утверждённый документ по итогам сверки | `skills/change-management` |

Устранение находок — тоже не задача этого skill. По каждой группе находок в отчёте указывается пишущий skill и владелец решения.

## Процесс

Шаги 1–4 — обязательная подготовка. Шаги 5–7 — сама сверка. Шаги 8–10 — фиксация результата.

### Шаг 1. Прочитать контекст

1. [rules/ai-guardrails.md](../../rules/ai-guardrails.md) — обязательный документ защиты от галлюцинаций; также [rules/linking.md](../../rules/linking.md), [rules/terminology.md](../../rules/terminology.md), [rules/requirements.md](../../rules/requirements.md).
2. [AGENTS.md](../../AGENTS.md), разделы «Source of truth» и «Когда анализировать services/».
3. [schemas/README.md](../../schemas/README.md) — формат ID и области уникальности.
4. [services/README.md](../../services/README.md) — как подключён код и что он означает как источник правды.
5. [docs/product/glossary.md](../../docs/product/glossary.md) — канонические термины **и помеченные «не использовать» синонимы**: они понадобятся как варианты поиска в коде.

### Шаг 2. Построить инвентарь требований

```bash
node scripts/validate-docs.mjs
node scripts/spec-inventory.mjs --scope <scope> --format json
node scripts/spec-inventory.mjs --scope <scope> --format md
```

`<scope>` — `feature:<name>`, `global` или область примера `example:<name>`. Без аргумента инвентаризуется всё.

- `--format md` даёт **каркас матрицы**: строки уже проставлены, колонки вердиктов пусты.
- **Строки матрицы задаёт скрипт.** Заполнять можно только колонки вердиктов; добавлять и удалять строки нельзя. Число строк в отчёте обязано совпадать с `requirements.length` инвентаря.
- `validateExit != 0` — спека сама не проходит валидацию (битые ID или ссылки). Прогон не отменяется, но **каждый вердикт помечается `provisional`**, и это указывается в первом абзаце отчёта.
- Непустой `pendingChanges` — часть требований затронута открытыми change proposals: сверка идёт против спеки, которая может сдвинуться. Отметить в Run metadata.

### Шаг 3. Проверить подключённость кода

`codeConnected: false` в инвентаре — переходить сразу к Шагу 9 в режиме деградации:

- отчёт формируется полностью, все строки инвентаря присутствуют;
- каждая строка получает вердикт `unverifiable`, reason code `no-code`;
- секция обратного прохода: `TBD: код не подключён в services/ — обратный проход не выполнялся.`;
- verified coverage выводится как `n/a`, **не** как `0 %` — измерения не было;
- **ни одной строки** `implemented`, `implemented-untested`, `partial`, `contradicted`, `not-implemented`;
- Next actions содержит ровно один пункт: подключить код (`repos.json` + `npm run pull` либо симлинк) и повторить прогон.

То же правило поштучно: если требование маршрутизируется в сервис, который не подключён, его вердикт — `unverifiable/no-code`, а не `not-implemented`. Отсутствие кода никогда не является доказательством отсутствия реализации.

### Шаг 4. Построить маршрутизацию «требование → код»

Отдельного файла соответствий нет и не заводится. Источники маршрутизации, в порядке надёжности:

1. **Явный якорь в коде** — литерал ID (`FR-001` в комментарии, в имени теста, в описании миграции). Наивысшая достоверность. Отсутствие якорей не значит ничего: конвенция необязательна.
2. **Существующая документация**:
   - [docs/architecture/components.md](../../docs/architecture/components.md) — путь `services/<service-name>` для каждого компонента;
   - `technical.md` feature, секция `Services involved`;
   - `api.md` feature — метод и путь endpoint'а как готовый ключ поиска маршрута;
   - [docs/architecture/data-model.md](../../docs/architecture/data-model.md) — имена сущностей как ключи поиска таблиц и моделей.
3. **Fallback** — искать по всем `services/*` и записать `ASSUMPTION: маршрутизация requirement → сервис не определена (components.md не заполнен). Requires confirmation.`

### Шаг 5. Прямой проход: spec → code

Для каждой строки инвентаря найти **место реализации** и **место теста**, каждое с `file:line` и дословной цитатой.

Закрытый словарь вердиктов:

| Verdict | Значение | Минимальное свидетельство |
|---------|----------|---------------------------|
| `implemented` | код реализует требование, тест это утверждает | код `file:line` + цитата, тест `file:line` + цитата |
| `implemented-untested` | код реализует, теста нет | код `file:line` + цитата, плюс запись о выполненном поиске теста |
| `partial` | часть условий реализована | свидетельство реализованной части **и** перечисление недостающих |
| `contradicted` | код делает обратное или нарушает требование | код `file:line` + цитата конфликтующего поведения |
| `not-implemented` | искали адекватно, не нашли | блок отрицательных доказательств (ниже) |
| `unverifiable` | из кода решить нельзя | reason code из закрытого списка |
| `not-applicable` | требование `deprecated` либо вне scope | флаг или scope, по которому исключено |
| `disputed` | проверяющий и опровергатель приводят несовместимые прочтения | оба прочтения, оба набора свидетельств |

Закрытый список reason codes для `unverifiable`:

```text
no-code                        сервис для этой области не подключён
requires-runtime-measurement   время, пропускная способность, перцентиль, доступность
requires-external-system       поведение во внешней системе (почта, SMS-шлюз)
requires-human-judgement       субъективная формулировка
spec-underspecified            проверяемая величина в самом требовании — TBD или ASSUMPTION
insufficient-search            поиск не удовлетворил протоколу отрицательных доказательств
out-of-scope                   вне запрошенной области
```

`spec-underspecified` — важнейший из них. Если требование говорит «после истечения интервала повторной отправки. TBD: длительность интервала», проверить соответствие невозможно: спека не называет величину. Вердикт — `unverifiable/spec-underspecified`, а конкретное значение из кода уходит в обратный проход как `undecided-in-spec`. Выдумывать «похоже, соответствует» запрещено.

Что считается свидетельством — зависит от типа требования:

| Тип | Свидетельство реализации | Свидетельство теста | По умолчанию, если не найдено |
|-----|--------------------------|---------------------|-------------------------------|
| FR | ветка кода, выполняющая действие: обработчик, метод сервиса, переход состояния | тест, утверждения которого повторяют Given/When/Then соответствующего AC | `not-implemented` |
| BR | **обеспечение** правила, а не наличие поля: проверка, guard, счётчик с порогом, уникальный индекс, middleware. Поле `attempts` не доказывает BR о лимите — доказывает сравнение с лимитом | негативный тест: правило нарушено → отказ | `not-implemented` |
| NFR | структурные (хеширование, отсутствие секрета в логах, шифрование) — проверяются статически; временные и статистические — нет | нагрузочный тест, SLO, алерт, константа тайм-аута | структурные — `not-implemented`; временные — `unverifiable/requires-runtime-measurement` |
| UI | компонент, экран, логика состояния | component-тест или e2e | `not-implemented`; фронтенд не подключён — `unverifiable/no-code` |
| API | регистрация маршрута: метод, путь, код ответа, схема запроса и ответа | контрактный или интеграционный тест по маршруту | `not-implemented` |
| ADR | код следует принятому решению, а не отклонённой альтернативе | — | `unverifiable/requires-human-judgement`, если у решения нет наблюдаемого отпечатка в коде |

Каждая строка дополнительно несёт `confidence` (`high` / `medium`) и `basis` (`marker` / `test` / `code` / `absent`). Уровня `low` нет: вердикт, который тянет только на `low`, — это `unverifiable`.

#### Протокол отрицательных доказательств

`not-implemented` — это **утверждение**, и его нужно заработать. Оно требует записанного блока: сколько файлов просмотрено и **не менее пяти различных выполненных запросов** из следующих источников:

1. литерал ID;
2. не менее трёх предметных существительных из формулировки требования — **и по-русски, и в правдоподобных английских или транслитерированных идентификаторах**; спека русская, код английский, и именно это несовпадение даёт основную массу ложных «не реализовано»;
3. канонический термин из glossary **вместе с его синонимами, помеченными «не использовать»**;
4. фрагмент пути и метод связанного `API-XXX`;
5. имена сущностей и таблиц из `data-model.md`;
6. имена тестовых файлов и строки `describe` / `it`.

**Записано меньше пяти запросов — вердикт принудительно становится `unverifiable/insufficient-search`, а не `not-implemented`.** Ответ на незнание — «неизвестно», никогда не «нет».

### Шаг 6. Обратный проход: code → spec

Не «прочитать код и увидеть недокументированное». Сначала **детерминированно перечислить наблюдаемые поверхности** — иначе поверхность будет придумана:

1. HTTP-поверхность: регистрации маршрутов — метод, путь, код ответа;
2. сохраняемое состояние: модели, миграции, таблицы, колонки, ограничения, уникальные индексы;
3. события, очереди, топики: producer и consumer;
4. фоновые задачи: расписания, планировщики и флаги их включения;
5. feature-флаги и ключи конфигурации, меняющие поведение;
6. пользовательские маршруты и экраны;
7. внешне наблюдаемые константы: тайм-ауты, TTL, число повторов, лимиты, максимум попыток, размеры страниц, ограничения параллелизма — именно эти величины спека и обязана определять;
8. коды ошибок и видимые пользователю сообщения.

**Явно не выносится в находки**: внутренние хелперы, рефакторинг, логирование, стиль, сборка, тестовые утилиты, обновления зависимостей. Сюда же — решения, невидимые снаружи: пропуск записи при совпадении хеша, отсутствие повторов при сбое, усечение служебных списков, порядок обхода. Без этого фильтра секция дрейфа превращается в шум и отчёт перестают читать.

Перечисление ограничивается **предметной областью scope**, а не всем модулем, в котором она реализована: требования про синхронизацию не обязаны описывать устройство индексатора и работу с git.

Пороги читаемости:

- находки `severity: low` в отчёт построчно **не выносятся** — только счётчик в сводке;
- если недокументированных `severity: high` больше двадцати пяти, это означает не дрейф, а **отсутствие спеки для этой части системы**. Такие находки группируются по видам поверхностей с указанием количества и нескольких представителей; построчное перечисление семидесяти пунктов нечитаемо и создаёт ложное впечатление, будто каждая строка требует отдельного решения.

Закрытый словарь вердиктов обратного прохода:

| Verdict | Значение |
|---------|----------|
| `covered` | поведение описано требованием — указывается ID **и дословная цитата требования** |
| `undocumented` | требования нет. Severity `high` для публичного endpoint'а, сохраняемого поля с бизнес-смыслом, фоновой задачи, видимого пользователю поведения; иначе `low`; чисто внутреннее — не выносится вовсе |
| `contradicts` | значение или поведение конфликтует с требованием; дублируется в секцию конфликтов и в строку прямого прохода как `contradicted` |
| `undecided-in-spec` | код содержит конкретное значение там, где спека говорит `TBD` или `ASSUMPTION` |
| `out-of-scope` | вне запрошенной области |

`undecided-in-spec` — самая ценная находка: **код отвечает на открытый вопрос спеки**. Оформляется как кандидат в FACT, ожидающий подтверждения человеком. Спека под код не переписывается.

Каждая находка обратного прохода разрешается ровно одним действием человека:

```text
(а) подтвердить ASSUMPTION или закрыть TBD          человек, затем skills/requirements
(б) открыть change proposal                          skills/change-management (обязательно для approved)
(в) исправить код                                    вне этого репозитория
(г) принять: поведение описано в другом месте        указать, где именно
```

### Шаг 7. Адверсарная проверка

Черновые вердикты проверяются опровергателями. У каждого — одна линза и задача **сломать** вердикт, а не подтвердить его.

| Опровергатель | Что атакует | Линза | Обязательная работа |
|---------------|-------------|-------|---------------------|
| R1 — покрытие | `not-implemented`, `partial`, `unverifiable/no-code`, `unverifiable/insufficient-search` | «Оно реализовано, просто называется иначе, лежит в другом сервисе, наследуется из фреймворка или обеспечивается ограничением БД, middleware либо декоратором» | не менее трёх **новых** запросов, которых не было у проверяющего |
| R2 — реализация | `implemented`, `implemented-untested` | «Приведённый код не удовлетворяет требованию: не та ветка, мёртвый код, выключено флагом, покрыто одно условие из двух, тест ничего не утверждает, тест мокает проверяемое» | прочитать **всю** объемлющую функцию и доказать достижимость от точки вызова |
| R3 — дрейф | `undocumented` обратного прохода | «Требование это описывает, только другими словами» | искать по **всему** инвентарю, включая другие области, а также `docs/product/business-rules.md`, `docs/product/non-functional-requirements.md`, `docs/api/`, `docs/architecture/`, синонимы из glossary |

Что опровергатель **не вправе** делать:

- **Понижать вердикт до `unverifiable`.** Его задача — доказать обратное («реализовано» против «не реализовано»), а не объявить вопрос непроверяемым. `unverifiable` — решение проверяющего. Иначе опровержение превращается в способ замять находку.
- **Ссылаться на `spec-underspecified`, если у самого требования нет пометки TBD или ASSUMPTION.** Пометки видны машинно — колонка «Флаги» в каркасе матрицы (`spec-inventory.mjs --format md`). Требование с собственной проверяемой величиной проверяемо, даже если соседнее требование той же feature оставляет что-то открытым.
- **Отменять вердикт из-за противоречия между двумя требованиями.** Внутренняя несогласованность спеки — находка `skills/documentation-review`, а не основание снять вердикт сверки. Фиксируется отдельной строкой в отчёте и адресуется туда.

Порог подтверждения:

- Вердикт **устоял, если его опровергатель не привёл контр-свидетельства**. Опровергатели не голосуют: «не смог опровергнуть» = подтверждено. Воздержанием нельзя размыть результат.
- Опровержение требует **свидетельства**, не мнения. При опровержении строка помечается `revised`, и показываются **оба** вердикта — исходный и пересмотренный.
- Обе стороны приводят код с несовместимыми прочтениями и ни одна не опровергнута — вердикт `disputed`, оба прочтения записаны дословно, решение за человеком. Не усредняется и не разрешается молча.
- Ограничения уверенности: вердикт на одном запросе или на файле, который не был прочитан целиком, — не выше `medium`. `implemented`, чьё тестовое свидетельство держится на моке проверяемого, понижается до `implemented-untested`.

### Шаг 8. Зафиксировать снимок

`file:line` в чужом репозитории без commit невоспроизводим. Из инвентаря в Run metadata переносятся: commit и чистота рабочего дерева спеки, для каждого сервиса — commit, признаки `symlink` и `dirty`, exit code валидатора, открытые change proposals.

### Шаг 9. Сформировать отчёт

Путь: `reports/verification/<YYYY-MM-DD>-<scope>.md`, рядом `<...>.evidence.json`. Коллизия по дате — суффикс `-2`; существующий отчёт не перезаписывается. Директория `reports/` в `.gitignore` и вне проверок валидатора.

Отчёт не кладётся в `docs/`: у него нет frontmatter, для него нет значения в `type`, он плотно ссылается на ID чужих областей и цитирует исходный код — это артефакт прогона, а не документ, проходящий жизненный цикл `draft → approved`.

Свидетельства из кода оформляются **инлайн-кодом** `` `path/to/file.ts:34` ``, не Markdown-ссылками: ссылка на файл в неподключённом у другого человека сервисе стала бы битой.

Секции отчёта:

```text
Заголовок и дисклеймер   ничего не изменялось; requirements outrank code
## Run metadata          scope, commit'ы, validateExit, сервисы, proposals, статус вердиктов
## Coverage summary      счётчики по вердиктам, разрез по типам, метрики с явным знаменателем
## Pass 1 — Spec → Code  матрица: строки из инвентаря, колонки вердиктов заполнены
## Pass 1 — Evidence     блок на каждый не-`implemented`: цитата требования, код, тест,
                         выполненные запросы, итог опровергателя
## Pass 2 — Code → Spec  undocumented; отдельной таблицей undecided-in-spec
## Conflicts             код против требования; обе стороны дословно; severity
## Unverifiable          ID, reason code, что нужно, чтобы стало проверяемым
## Disputed              несовместимые прочтения либо `none`
## Appendix              полный журнал запросов — для воспроизводимости
## Next actions          находка → действие → владелец или skill
```

Метрики выводятся с явным знаменателем:

```text
verified coverage = (implemented + implemented-untested) / (всего − unverifiable − not-applicable)
test coverage     = implemented / (implemented + implemented-untested)
```

`unverifiable` исключены из знаменателя намеренно: иначе метрика улучшалась бы за счёт непроверяемых требований.

Отдельным списком выносятся ID с `unverifiable` по причинам `requires-human-judgement` и `spec-underspecified`: [rules/requirements.md](../../rules/requirements.md) требует, чтобы требование было проверяемым, поэтому непроверяемая формулировка — это находка качества спеки, адресуемая `skills/requirements`.
