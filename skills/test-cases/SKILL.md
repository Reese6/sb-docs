# Skill: test-cases

Пишет тест-кейсы для ручного тестирования feature и сохраняет их в один файл `test-cases/<feature-name>.md` по шаблону [templates/test-cases.md](../../templates/test-cases.md). Единственный источник информации — документация в `docs/`. **Читать код запрещено**: тест-кейсы проверяют требуемое поведение из документации, а не текущую реализацию.

Формат кейса — классический QA-шаблон: ID, название, приоритет, требования, предусловия, шаги, ожидаемый результат.

Два режима: **feature** — кейсы по документации feature целиком; **change** — инкрементальное обновление кейсов затронутых features после применённого (applied) change proposal.

## Когда использовать

- Пользователь просит тест-кейсы, чек-лист ручного тестирования или «что нужно проверить» по feature.
- Feature имеет `requirements.md` (без требований тест-кейсы не пишутся).
- После утверждения или содержательного изменения `requirements.md`, `ui.md`, `api.md` — чтобы актуализировать кейсы.
- После apply change proposal (`skills/change-management`) — обновить кейсы затронутых features и получить список «что перетестировать» (режим change).

## Когда не использовать

| Задача | Правильный skill |
|--------|------------------|
| Описать проблему, пользователей, сценарии, scope | `skills/product-documentation` |
| Формализовать требования (FR/BR/NFR) | `skills/requirements` |
| Описать поведение интерфейса | `skills/ui-requirements` |
| Описать контракт API | `skills/api-requirements` |
| Описать реализацию решения | `skills/technical-documentation` |
| Зафиксировать архитектурное решение (ADR) | `skills/architecture-decisions` |
| Проверить документацию | `skills/documentation-review` |
| Содержательно изменить утверждённый документ | `skills/change-management` |
| Комплексная новая feature | `skills/documentation-orchestrator` |

Автоматизация тестов (код автотестов) — вне scope этого skill и репозитория.

## Запрещено

Эти правила важнее любых других соображений. Нарушение любого из них — ошибка выполнения skill.

1. **НЕ открывать `services/`** — ни один файл, включая README вложенных репозиториев.
2. **НЕ открывать файлы кода** — `*.ts`, `*.js`, `*.mjs`, `*.go`, `*.java`, `*.py`, `*.sql` и любые другие. `scripts/` не читать; единственное исключение — запуск команды `node scripts/validate-docs.mjs` на шаге 8.
3. **НЕ читать `technical.md`** — тест-кейсы описывают требуемое поведение, а не реализацию. Change proposals (`docs/changes/`, включая архив) — документация: читать можно и нужно в режиме change.
4. **НЕ придумывать значения** — лимиты, тайминги, тексты ошибок, названия кнопок, форматы. Значения нет в документации — писать `TBD: <что неизвестно>` прямо в предусловии, шаге или ожидаемом результате. `ASSUMPTION` из документации использовать только с пометкой, что значение не подтверждено.
5. **НЕ изменять файлы в `docs/`, `rules/`, `schemas/`, `templates/`** — skill создаёт и изменяет только файлы в `test-cases/`.

## Процесс

Выполнять шаги строго по порядку, не пропуская.

### Шаг 1. Прочитать контекст

1. [rules/ai-guardrails.md](../../rules/ai-guardrails.md) — обязательный документ защиты от галлюцинаций.
2. [docs/product/glossary.md](../../docs/product/glossary.md) — термины употреблять только по glossary.
3. Шаблон результата: [templates/test-cases.md](../../templates/test-cases.md).

### Шаг 2. Определить режим

- Запрос про feature (названа feature или директория `docs/features/<feature-name>/`) → режим **feature**: выполнять шаги 3–8.
- Запрос про change (назван change, change proposal или путь в `docs/changes/`) → режим **change**: перейти к секции «Режим change» ниже.
- Непонятно — спросить пользователя. Не угадывать.

### Шаг 3. Определить feature и прочитать её документацию

1. Определить `<feature-name>` из запроса пользователя. Непонятно, какая feature, — показать пользователю список директорий `docs/features/` и спросить. Не угадывать.
2. Прочитать документы feature в этом порядке: `docs/features/<feature-name>/README.md`, `product.md`, `requirements.md`, затем `ui.md` и `api.md`, если существуют. `technical.md` не читать (см. «Запрещено»).
3. Прочитать глобальный контекст, на который ссылаются документы feature: [docs/product/business-rules.md](../../docs/product/business-rules.md), при наличии ссылок — `docs/api/errors.md`, `docs/api/conventions.md`.
4. Если `requirements.md` отсутствует — остановиться и сообщить пользователю: сначала `skills/requirements`.

### Шаг 4. Выписать все требования

Составить полный список ID из прочитанных документов: все `FR-XXX`, `BR-XXX`, `NFR-XXX` из `requirements.md`, все `UI-XXX` из `ui.md`, все `API-XXX` из `api.md`, все Acceptance Criteria (`AC для FR-XXX: ...`). Этот список — основа таблицы Coverage: каждый ID обязан попасть либо в кейсы, либо в секцию `Not covered by manual testing` с причиной.

### Шаг 5. Сгенерировать кейсы по правилам преобразования

Применять правила по порядку, к каждому элементу списка из шага 4:

1. **Каждый AC → минимум один TC.** Прямое преобразование: `Given` → предусловия, `When` → шаги, `Then` → ожидаемый результат.
2. **Каждый FR без AC → минимум один позитивный TC** (основной успешный сценарий). Условия в формулировке FR («при», «если», «только после», «не более») → дополнительные негативные и граничные TC: что происходит при нарушении условия.
3. **Каждое UI-требование → TC** на описанные в `ui.md` состояния экранов (пустое, загрузка, ошибка) и валидацию полей.
4. **Каждая ошибка из `api.md`**, воспроизводимая действиями пользователя через интерфейс, → негативный TC. Ошибки, недостижимые вручную, — в `Not covered by manual testing`.
5. **Каждый BR → TC**, проверяющий, что правило соблюдается (и негативный TC на попытку его нарушить).
6. **NFR → TC только если проверяем вручную** (например, наблюдаемое поведение). Остальные NFR — в `Not covered by manual testing` с причиной («требует нагрузочного тестирования», «требует доступа к логам»).

Один TC проверяет одну вещь. Несколько проверок — несколько TC.

### Шаг 6. Проставить приоритеты

Фиксированная схема, без исключений:

- **Высокий** — основной успешный сценарий, безопасность, потеря данных или денег.
- **Средний** — негативные и альтернативные сценарии.
- **Низкий** — граничные значения, редкие комбинации, косметика.

### Шаг 7. Записать файл

Создать `test-cases/<feature-name>.md` строго по структуре [templates/test-cases.md](../../templates/test-cases.md): frontmatter, `Sources`, `Coverage`, `Test Cases`, `Not covered by manual testing`, `Open Questions`. Нумерация `TC-001, TC-002, ...` — сквозная, без пропусков. Файл уже существует — перезаписать целиком, сохранив прежние номера TC для не изменившихся кейсов.

### Шаг 8. Проверить результат

Запустить `node scripts/validate-docs.mjs` — команда ловит битые относительные ссылки; exit code должен быть `0`. Затем пройти чек-лист:

- [ ] Каждый AC покрыт хотя бы одним TC.
- [ ] Каждый FR, BR, UI, API, NFR из шага 4 есть в таблице Coverage или в `Not covered by manual testing` с причиной.
- [ ] У каждого TC заполнены все поля: название, приоритет, требования, предусловия, шаги, ожидаемый результат.
- [ ] Каждый TC ссылается хотя бы на один ID требования или AC.
- [ ] Ни одно значение не выдумано: каждое взято из документации либо помечено `TBD`.
- [ ] Не открыт ни один файл кода, ничего в `services/`, не прочитан `technical.md`.
- [ ] Файлы вне `test-cases/` не изменены.
- [ ] Термины — по glossary.
- [ ] (режим change) Каждый ID из Deltas и Assigned IDs учтён: новый TC, переписанный TC или пометка `DEPRECATED`.
- [ ] (режим change) Номера TC не переиспользованы и не перенумерованы.
- [ ] (режим change) Список «что перетестировать» передан пользователю.

## Режим change

Обновляет кейсы после применения change proposal. Работает **только с применёнными изменениями** (`## Status: applied`): реальные ID уже присвоены, дельты уже внесены в документацию features. Кейсы по неприменённому proposal не пишутся — в них попали бы плейсхолдеры `FR-NEW-N` и ещё не существующее поведение.

1. **Найти proposal.** Искать `proposal.md` сначала в `docs/changes/archive/*-<change-name>/` (применённые изменения переносятся в архив), затем в `docs/changes/<change-name>/`. Не найден — показать пользователю список директорий `docs/changes/` и `docs/changes/archive/` и спросить.
2. **Проверить статус.** Прочитать секцию `## Status` в `proposal.md`:
   - `applied` → продолжать;
   - `proposed` или `approved` → остановиться и сообщить: кейсы пишутся после apply, сначала `skills/change-management` (режим apply);
   - `rejected` → остановиться и сообщить: изменение отклонено, кейсы не нужны.
3. **Собрать scope из proposal.** Выписать: затронутые features (секция `Affected Documents`), реальные ID новых требований (секция `Assigned IDs`, соответствие `FR-NEW-N → FR-XXX`), изменённые и удалённые ID (секция `Deltas`, подсекции `MODIFIED` и `REMOVED`), связанные ID для регресса (секция `Impact`).
4. **Обновить файл каждой затронутой feature.** Прочитать документацию feature (шаг 3) и инкрементально обновить `test-cases/<feature-name>.md`:
   - файла нет — создать целиком по шагам 3–7;
   - **ADDED** → написать новые TC по правилам шага 5 для каждого нового ID (из `Assigned IDs`); номера — следующие свободные, существующие TC не перенумеровывать;
   - **MODIFIED** → найти по таблице Coverage все TC, ссылающиеся на изменённые ID, и переписать их по новой формулировке требования из документации;
   - **REMOVED** → TC, проверяющие только deprecated-требование, пометить: заголовок `### TC-00X: [DEPRECATED — <change-name>] <название>`, в Coverage — `deprecated`; текст кейса не удалять, номер не переиспользовать.
5. **Составить список «что перетестировать»** для пользователя:
   - новые TC (по ADDED) — выполнить;
   - переписанные TC (по MODIFIED) — выполнить заново;
   - TC, ссылающиеся на ID из `Impact`, — регресс, выполнить без изменений кейсов;
   - deprecated TC — больше не выполнять.
6. **Проверить результат** — шаг 8, включая пункты «(режим change)».

## Пример преобразования AC → TC

Источник — [templates/examples/password-recovery/requirements.md](../../templates/examples/password-recovery/requirements.md):

> AC для FR-001, FR-002: Given учётная запись с email `user@example.com` существует, When пользователь запрашивает восстановление с этим email, Then создаётся сессия восстановления и на email отправляется OTP.

Результат:

```markdown
### TC-001: Запрос восстановления пароля с существующим email

| Поле | Значение |
|------|----------|
| Приоритет | Высокий |
| Требования | FR-001, FR-002, AC для FR-001, FR-002 |
| Предусловия | Учётная запись с email `user@example.com` существует; пользователь не аутентифицирован |

**Шаги:**

1. Открыть экран запроса восстановления пароля (UI-001).
2. Ввести email `user@example.com`.
3. Отправить запрос восстановления.

**Ожидаемый результат:** Создана сессия восстановления; на `user@example.com` отправлен OTP.
```

Пример обращения с неизвестным значением — в требованиях BR-003 число неверных вводов не подтверждено (`ASSUMPTION: 5`), поэтому в кейсе оно не используется как факт:

```markdown
### TC-002: Отклонение OTP после превышения числа неверных вводов

| Поле | Значение |
|------|----------|
| Приоритет | Высокий |
| Требования | BR-003, AC для BR-003 |
| Предусловия | Активная сессия восстановления; исчерпано допустимое число неверных вводов OTP (`TBD: значение не подтверждено, ASSUMPTION — 5`) |

**Шаги:**

1. Ввести любой OTP ещё раз.

**Ожидаемый результат:** Ввод отклонён; сессия восстановления завершена.
```

Полный референсный файл тест-кейсов этой feature — [templates/examples/password-recovery/test-cases.md](../../templates/examples/password-recovery/test-cases.md): все AC покрыты, каждый ID — в таблице Coverage, неизвестные значения помечены `TBD`/`ASSUMPTION`.

Завершая работу, сообщить пользователю: созданный или обновлённый файл, количество TC, таблицу Coverage, список `TBD`/`ASSUMPTION`, попавших в кейсы, содержимое `Not covered by manual testing`, а в режиме change — список «что перетестировать» из шага 5 режима change.
