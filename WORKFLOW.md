# WORKFLOW

Пошаговый workflow сотрудника, ведущего документацию с помощью AI-агента: путь от новой задачи до коммита, примеры промптов, точки контроля.

Разграничение с соседними документами:

- [AGENTS.md](AGENTS.md) — инструкция для AI-агента: карта репозитория, guardrails, выбор skill.
- [CONTRIBUTING.md](CONTRIBUTING.md) — правила процесса: статусы, порог change proposal, формат коммитов.
- Этот документ — сценарии работы для человека: что писать агенту и что проверять в его ответах.

Работа ведётся командами `/feature-*` из `.gigacode/commands/`: одна команда — один документ feature. Порядок вызовов задаёт человек, полная таблица «команда → skill → следующая» — [.gigacode/README.md](.gigacode/README.md). Где команды нет (ADR, change proposal), skill вызывается по имени.

Сквозной пример в промптах — вымышленная feature `password-recovery`.

## Принципы работы

- Человек — источник фактов и единственная утверждающая сторона. Агент никогда не ставит `approved` (раздел «Статусы документов» в [CONTRIBUTING.md](CONTRIBUTING.md)).
- Один вызов команды — один документ. Команда может остановиться с вопросами (не больше пяти, одним списком) или из-за отсутствия входа — это нормальное поведение, а не сбой.
- Отчёт каждой команды заканчивается строкой «Следующая команда: …» — это и есть навигация по пайплайну. Отдельной команды статуса нет.
- Одна задача — одна сессия агента — один коммит (раздел «Коммиты» в [CONTRIBUTING.md](CONTRIBUTING.md)).
- Маленькие итерации: один промпт — одно намерение. Результат проверяется после каждого шага, а не в конце сессии.
- Каждый `ASSUMPTION` и `TBD` в ответе агента требует реакции человека: подтвердить, опровергнуть или осознанно оставить. Категории информации — [rules/ai-guardrails.md](rules/ai-guardrails.md).
- Правки вносятся через агента, а не руками: пишущие skills обновляют cross-reference и traceability. Руками человек меняет только `status: approved` в frontmatter и решение `## Status` в proposal.
- Результат каждой сессии проверяется: `/feature-review` и `node scripts/validate-docs.mjs`.

## Как формулировать промпты

- Первое слово аргументов команды — имя feature в kebab-case, остальное — факты и намерение: `/feature-requirements password-recovery код живёт 5 минут`.
- Называть намерение — что должно измениться в продукте, а не какой файл отредактировать. Файл определяется выбранной командой.
- Давать факты сразу и помечать их как факты: лимиты, сроки, форматы, источники. Всё, что не дано, агент обязан пометить `ASSUMPTION` или `TBD` — это ожидаемое поведение, а не недостаток.
- Явно ограничивать scope: какие файлы менять, какие не трогать.
- Формулировать критерий готовности: по какому признаку результат считается принятым.

Выбор сценария по намерению:

| Намерение | Команда / skill | Сценарий |
|-----------|-----------------|----------|
| Новая feature целиком | цепочка `/feature-*` | 1 |
| Автоматический маршрут по всем стадиям | skill `documentation-orchestrator` | 1, врезка |
| Один документ feature | своя `/feature-<документ>` | 2 |
| Архитектурное решение (ADR) | skill `architecture-decisions` (команды нет) | 2 |
| Правка `draft`/`review` или MINOR-правка `approved` | команда этого документа | 3 |
| Содержательное изменение `approved`-документа | skill `change-management` | 4 |
| Промоут результатов в глобальные документы | `/feature-apply` | 4, врезка |
| Проверка документации | `/feature-review` | 5 |
| Готово, надо закоммитить | — | 6 |

## Что проверять в каждом ответе агента

Единый чеклист; на него опираются все сценарии:

- [ ] Итоговый отчёт содержит списки `ASSUMPTION` (ждут подтверждения) и `TBD` (ждут ответа). Ответить на каждый пункт.
- [ ] Последняя строка отчёта — «Следующая команда: …». Строки нет — команда выполнена не по своему `SKILL.md`.
- [ ] Статусы корректны: новые документы — `draft`; изменённые `approved`-документы переведены в `review`; `approved` «сам» не появился.
- [ ] Существующие requirement ID не изменены; новые ID — следующие свободные номера (стандарт — [schemas/README.md](schemas/README.md)).
- [ ] Отчёт review передан целиком; находки не «исправлены» молча.
- [ ] Scope не расширен: в изменениях только запрошенное.

Отдельно — подозрение на выдуманное значение: конкретное число, формат или код ошибки, который человек не давал и которого нет в связанных документах. Потребовать источник или пометку `ASSUMPTION`/`TBD` (признак нарушения — [rules/ai-guardrails.md](rules/ai-guardrails.md)).

## Сценарий 1. Новая feature с нуля

Feature собирается по одному документу за вызов. Шаги идут по порядку; шаги 4 и 5 пропускаются, если у feature нет своих сущностей или интерфейса.

### Цепочка команд

1. `/feature-create` — директория feature и три заготовки (`README.md`, `product.md`, `requirements.md`).

```text
/feature-create password-recovery восстановление пароля по SMS
```

Контроль: feature появилась в списке в [docs/features/README.md](docs/features/README.md); `TBD` в заготовках — норма, отвечать на них не нужно.

2. `/feature-product` — проблема, пользователи, сценарии, метрики.

```text
/feature-product password-recovery пользователь запрашивает код на привязанный
номер телефона, вводит его и задаёт новый пароль
```

3. `/feature-requirements` — FR, BR, NFR со стабильными ID.

```text
/feature-requirements password-recovery подтверждённые факты: код живёт 5 минут,
не более 3 запросов кода в час
```

4. `/feature-model` — одна сущность за вызов; только если feature вводит или меняет сущности. Без имени сущности команда составляет список из требований и останавливается; файлы при этом не меняются.

```text
/feature-model password-recovery
```

```text
/feature-model password-recovery otp-code
```

Контроль: создан ровно один файл `model/<entity>.md` плюс строка в индексе `model/README.md`; существующие сущности из [docs/architecture/data-model/](docs/architecture/data-model/) переиспользованы ссылкой, а не переписаны в feature.

5. `/feature-ui` — экраны, состояния, валидация; только при наличии интерфейса.

```text
/feature-ui password-recovery три экрана: запрос кода, ввод кода, новый пароль
```

6. `/feature-api` — один метод за вызов. Без метода и пути команда составляет список методов из требований и останавливается; документ при этом не меняется.

```text
/feature-api password-recovery
```

```text
/feature-api password-recovery POST /auth/password-reset/request
```

Контроль: создан ровно один файл `api/<method>-<имя>.md` плюс строка в индексе `api/README.md`, остальные файлы не тронуты; роли — только из [docs/product/roles.md](docs/product/roles.md).

7. `/feature-technical` — реализация, интеграции, хранение. Шаг можно отложить до согласования требований.

```text
/feature-technical password-recovery
```

8. `/feature-review` — отчёт о находках, документы не правятся. Дальше — Сценарий 5.

```text
/feature-review password-recovery
```

9. `/feature-apply` — промоут в глобальные документы; только после того, как человек выставил `approved`. Дальше — врезка в Сценарии 4.

```text
/feature-apply password-recovery
```

### Точки контроля после каждого шага

- Ответить на `ASSUMPTION` и `TBD` из отчёта явно, по пунктам:

```text
ASSUMPTION про 3 попытки ввода кода подтверждаю — это факт. Длину кода
не выдумывай, оставь TBD: уточню у команды безопасности.
```

- Остановка команды (нет входа, ждёт подтверждения) — правильное поведение: дать недостающую информацию или отложить работу, но не разрешать «додумать ради завершения».
- `node scripts/validate-docs.mjs` → exit code `0`.
- Сверить ответ с чеклистом «Что проверять в каждом ответе агента».

### Автоматический маршрут

Skill `documentation-orchestrator` ([.gigacode/skills/documentation-orchestrator/SKILL.md](.gigacode/skills/documentation-orchestrator/SKILL.md)) проходит все стадии сам: обязан показать план до запуска, план можно сократить.

```text
План подтверждаю, но стадию Technical убери — реализацию опишем после
согласования требований. Стадии Product, Requirements, UI, API запускай.
```

Маршрут подходит, когда агент уверенно держит длинный пайплайн; на слабых моделях надёжнее цепочка команд выше. Точки контроля те же, плюс проверка плана: нет ли стадий «на всякий случай», отмечены ли затрагиваемые `approved`-документы.

## Сценарий 2. Отдельный документ

### Когда

Запрос укладывается в один документ — вызывается его команда, без прохода всей цепочки.

### Промпты

```text
/feature-requirements password-recovery формализуй требования по product.md.
Работай только с requirements.md — ui.md и api/ не трогай.
```

```text
/feature-api password-recovery POST /auth/password-reset/confirm — проверка кода
и установка нового пароля. Формат ошибок дам после черновика, пока помечай TBD.
```

Skill вызывается по имени только там, где команды нет:

```text
Зафиксируй архитектурное решение по выбору канала доставки кода для feature
password-recovery — skill architecture-decisions.
```

Границы каждого skill — секции «Когда использовать» / «Когда не использовать» его `SKILL.md`; routing — раздел «Как определить нужный skill» в [AGENTS.md](AGENTS.md).

### Точки контроля

- Команда останавливается без входов (например, нет заполненного `product.md` для формализации требований). Создать вход своей командой (`/feature-product`), а не заставлять агента обходить остановку.
- Review нужен и после одного документа (раздел «Когда запускать review» в [AGENTS.md](AGENTS.md)) — Сценарий 5.

## Сценарий 3. Правка существующего draft/review-документа

### Когда

- Любые правки `draft`- и `review`-документов.
- MINOR-правки `approved`-документов: опечатки, ссылки, формулировки без изменения смысла. Порог — раздел «Изменение утверждённых документов» в [CONTRIBUTING.md](CONTRIBUTING.md).

Содержательное изменение `approved`-документа — Сценарий 4.

### Промпты

Правка заказывается командой того же документа:

```text
/feature-requirements password-recovery измени FR-003: интервал повторного
запроса кода — 60 секунд (подтверждённый факт, раньше был TBD). Обнови
связанные UI/API-требования и traceability. Больше ничего не меняй.
```

```text
/feature-requirements password-recovery добавь требование: после 3 неверных
вводов кода сессия восстановления блокируется. Число 3 — факт от product owner.
Существующие требования не переформулируй.
```

### Как итерироваться

Формула точной правки: ID или цитата текущего текста, что не так, как должно быть, источник факта.

```text
/feature-requirements password-recovery FR-004 сформулирован неатомарно: запрос
кода и проверка кода склеены в одном требовании. Разбей на два; нумерацию
существующих требований не меняй.
```

Промпты без критерия готовности — «улучши», «перепиши получше», «наведи порядок» — не использовать: они провоцируют переписывание документа целиком и расширение scope.

### Точки контроля

- Diff минимален: изменено только запрошенное (правило минимального изменения — [CONTRIBUTING.md](CONTRIBUTING.md)).
- Существующие ID сохранены; cross-reference и traceability обновлены.
- Статус и версия изменённого документа — по правилам [schemas/README.md](schemas/README.md).

## Сценарий 4. Изменение approved-документа (change proposal)

### Когда обязателен proposal

При содержательном изменении `approved`-документа: добавление, изменение или удаление требований. Порог — раздел «Изменение утверждённых документов» в [CONTRIBUTING.md](CONTRIBUTING.md), процесс — [.gigacode/skills/change-management/SKILL.md](.gigacode/skills/change-management/SKILL.md). Команды у этого skill нет — вызывать по имени.

### Этап 1. Создать proposal

```text
Нужно содержательно изменить утверждённый requirements.md feature
password-recovery: код теперь доставляется по SMS или e-mail на выбор
пользователя. Подготовь change proposal, сами целевые документы не трогай.
```

Проверить в результате:

- дельты разложены по ADDED / MODIFIED / REMOVED;
- в MODIFIED «Было:» — дословная текущая формулировка (сверить с документом);
- новые требования — placeholders `<TYPE>-NEW-<n>`, реальные ID не присвоены;
- неподтверждённые значения внутри дельт помечены `ASSUMPTION`/`TBD`.

### Этап 2. Решение человека

Единственная ручная правка файлов в этом workflow: человек сам выставляет решение в `proposal.md` — `## Status: approved` (или `rejected`) в теле и `status` в frontmatter. Агент не применяет `proposed`-proposal и не «дозревает» его статус.

### Этап 3. Применить proposal

```text
Proposal docs/changes/password-recovery-email-otp/proposal.md я утвердил
(Status: approved). Примени его.
```

Проверить в результате:

- секция Assigned IDs заполнена: каждый placeholder получил реальный ID;
- целевые документы: MAJOR bump версии, статус `review`;
- REMOVED-требования помечены `deprecated`, не удалены;
- директория proposal перенесена в `docs/changes/archive/`;
- review прогнан, отчёт передан целиком.

Повторный перевод целевых документов в `approved` — отдельное решение человека (Сценарий 6).

### Промоут в глобальные документы

`/feature-apply` переносит результаты `approved`-документов feature наружу: новые сущности из `model/` — в `docs/architecture/data-model/<entity>.md`, сервисные и внешние API из `api/` — в `docs/api/services/<service>.md`, плюс обновляет индексы.

```text
/feature-apply password-recovery
```

- Цель ещё не существует — создаётся файл в статусе `draft`.
- Цель уже `approved` — команда не правит её, а готовит change proposal; применяет его `change-management` (этапы 2–3 выше).
- Индексы или файлы `model/` и `api/` не в статусе `approved` — команда останавливается: статус ставит человек.

## Сценарий 5. Ревью и работа с замечаниями

### Когда запускать

После содержательного изменения requirements/ui/api/technical, перед переводом документа в `approved` и в конце любой сессии с изменениями. Полный список — раздел «Когда запускать review» в [AGENTS.md](AGENTS.md).

### Промпт

```text
/feature-review password-recovery
```

### Как читать отчёт

Формат отчёта — [.gigacode/skills/documentation-review/SKILL.md](.gigacode/skills/documentation-review/SKILL.md). Что означают находки для человека:

- `ERROR` — нарушение правил: битая ссылка, противоречие, непокрытое требование, сущность описана в feature вместо ссылки на глобальную, роль не из `roles.md`, подозрение на галлюцинацию. Требует решения до коммита.
- `WARNING` — качество: неатомарность, неизмеримая формулировка, отклонение от glossary. Решить: исправить сейчас или осознанно отложить.
- Четыре итоговых списка (Unresolved TBD, Unconfirmed assumptions, Broken references, Coverage gaps) — открытые вопросы к человеку, а не дефекты.
- `TBD` в незаполненных заготовках свежей feature находкой не считается: это ожидаемое состояние после `/feature-create`.

### Работа с находками

Review сам ничего не исправляет; решение по каждой находке принимает человек, исправления заказываются командой соответствующего документа:

```text
/feature-api password-recovery по отчёту review: ERROR про непокрытый FR-007
исправь — добавь требование на проверку кода. WARNING про синоним
«одноразовый код» не трогай: внесу термин в glossary отдельной задачей.
```

- Находку допустимо мотивированно отклонить — причина фиксируется в ответе агенту.
- После исправлений — повторный `/feature-review` затронутых документов.

## Сценарий 6. Финальная проверка и коммит

### Проверка

```text
Запусти node scripts/validate-docs.mjs. Есть ошибки — исправь и запусти
снова, покажи итоговый вывод.
```

Затем прочитать diff глазами — последняя линия защиты от выдуманных значений:

```text
Покажи git status и git diff по docs/features/password-recovery/.
```

### Чеклист перед коммитом

- [ ] `node scripts/validate-docs.mjs` — exit code `0`.
- [ ] Review прогнан после последнего содержательного изменения.
- [ ] На каждый `ASSUMPTION` дан ответ; оставшиеся `TBD` оставлены осознанно.
- [ ] Статусы и версии корректны; `approved` не появился без решения человека.
- [ ] Diff прочитан; в нём только запрошенное изменение.
- [ ] Изменения — один логический блок; иначе разбить на несколько коммитов.

### Коммит

```text
Закоммить изменения по feature password-recovery одним коммитом
с сообщением по конвенции из CONTRIBUTING.md.
```

Формат сообщения — раздел «Коммиты» в [CONTRIBUTING.md](CONTRIBUTING.md).

### Перевод в approved

Отдельное действие и отдельный коммит, после review без блокирующих находок:

1. Человек сам меняет `status` документа в frontmatter на `approved` (правила статусов и версий — [schemas/README.md](schemas/README.md)).
2. Запустить `node scripts/validate-docs.mjs`.
3. Закоммитить отдельным коммитом.

## Если что-то пошло не так

- Команда ответила «Укажи имя feature» — первым словом аргументов должно идти имя feature в kebab-case, остальное — запрос.
- Потерялось место в пайплайне — смотреть строку «Следующая команда» в последнем отчёте либо таблицу команд в [.gigacode/README.md](.gigacode/README.md).
- Команда отработала не по своему skill (отчёта по шаблону нет, шаги пропущены) — назвать skill явно: «выполни `.gigacode/skills/<skill>/SKILL.md` целиком».
- Агент вписал конкретное значение без источника — указать на [rules/ai-guardrails.md](rules/ai-guardrails.md) и потребовать заменить значение на `TBD`/`ASSUMPTION` либо назвать источник.
- Агент переписал документ целиком — откатить (`git checkout -- <файл>`) и повторить промпт с явным ограничением scope.
- `validate-docs` падает — скопировать вывод в промпт целиком: формат `файл:строка [КОД] сообщение` самодостаточен для исправления.
- Агент сам поставил `approved` или применил неутверждённый proposal — откатить изменение и указать на нарушение: статусы решений выставляет только человек.
