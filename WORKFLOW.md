# WORKFLOW

Пошаговый workflow сотрудника, ведущего документацию с помощью AI-агента: путь от новой задачи до коммита, примеры промптов, точки контроля.

Разграничение с соседними документами:

- [AGENTS.md](AGENTS.md) — инструкция для AI-агента: карта репозитория, guardrails, выбор skill.
- [CONTRIBUTING.md](CONTRIBUTING.md) — правила процесса: статусы, порог change proposal, формат коммитов.
- Этот документ — сценарии работы для человека: что писать агенту и что проверять в его ответах.

Сквозной пример в промптах — вымышленная feature `password-recovery`; заполненный эталон такой feature — `templates/examples/password-recovery/`.

## Принципы работы

- Человек — источник фактов и единственная утверждающая сторона. Агент никогда не ставит `approved` (раздел «Статусы документов» в [CONTRIBUTING.md](CONTRIBUTING.md)).
- Одна задача — одна сессия агента — один коммит (раздел «Коммиты» в [CONTRIBUTING.md](CONTRIBUTING.md)).
- Маленькие итерации: один промпт — одно намерение. Результат проверяется после каждого шага, а не в конце сессии.
- Каждый `ASSUMPTION` и `TBD` в ответе агента требует реакции человека: подтвердить, опровергнуть или осознанно оставить. Категории информации — [rules/ai-guardrails.md](rules/ai-guardrails.md).
- Правки вносятся через агента, а не руками: пишущие skills обновляют cross-reference и traceability. Руками человек меняет только `status: approved` в frontmatter и решение `## Status` в proposal.
- Результат каждой сессии проверяется: skill `documentation-review` и `node scripts/validate-docs.mjs`.

## Как формулировать промпты

- Называть feature и намерение — что должно измениться в продукте, а не какой файл отредактировать. Агент выбирает skill сам (раздел «Как определить нужный skill» в [AGENTS.md](AGENTS.md)); известный заранее skill можно назвать явно.
- Давать факты сразу и помечать их как факты: лимиты, сроки, форматы, источники. Всё, что не дано, агент обязан пометить `ASSUMPTION` или `TBD` — это ожидаемое поведение, а не недостаток.
- Явно ограничивать scope: какие файлы менять, какие не трогать.
- Формулировать критерий готовности: по какому признаку результат считается принятым.

Выбор сценария по намерению:

| Намерение | Сценарий |
|-----------|----------|
| Новая feature целиком | Сценарий 1 |
| Один документ (product, requirements, ui, api, technical, ADR) | Сценарий 2 |
| Правка `draft`/`review` или MINOR-правка `approved` | Сценарий 3 |
| Содержательное изменение `approved`-документа | Сценарий 4 |
| Проверка документации | Сценарий 5 |
| Готово, надо закоммитить | Сценарий 6 |
| Сверить документацию с реальным кодом | Сценарий 7 |

## Что проверять в каждом ответе агента

Единый чеклист; на него опираются все сценарии:

- [ ] Итоговый отчёт содержит списки `ASSUMPTION` (ждут подтверждения) и `TBD` (ждут ответа). Ответить на каждый пункт.
- [ ] Статусы корректны: новые документы — `draft`; изменённые `approved`-документы переведены в `review`; `approved` «сам» не появился.
- [ ] Существующие requirement ID не изменены; новые ID — следующие свободные номера (стандарт — [schemas/README.md](schemas/README.md)).
- [ ] Отчёт review передан целиком; находки не «исправлены» молча.
- [ ] Scope не расширен: в изменениях только запрошенное.

Отдельно — подозрение на выдуманное значение: конкретное число, формат или код ошибки, который человек не давал и которого нет в связанных документах. Потребовать источник или пометку `ASSUMPTION`/`TBD` (признак нарушения — [rules/ai-guardrails.md](rules/ai-guardrails.md)).

## Сценарий 1. Новая feature с нуля

Комплексная задача: постановка, требования, интерфейс, API. Работает skill `documentation-orchestrator` ([skills/documentation-orchestrator/SKILL.md](skills/documentation-orchestrator/SKILL.md)); называть его в промпте не обязательно — агент выберет его сам по комплексному запросу.

### Промпт

Намерение, сценарий использования, подтверждённые факты, границы:

```text
Задокументируй новую feature «восстановление пароля по SMS»: пользователь
запрашивает код на привязанный номер телефона, вводит его и задаёт новый
пароль. Подтверждённые факты: код живёт 5 минут, не более 3 запросов кода
в час. Есть интерфейс и API; техническую реализацию пока не описываем.
```

### Ход работы и точки контроля

- Оркестратор обязан показать план стадий до запуска. Проверить план: нет ли стадий «на всякий случай», отмечены ли затрагиваемые `approved`-документы. Подтвердить или сократить:

```text
План подтверждаю, но стадию Technical убери — реализацию опишем после
согласования требований. Стадии Product, Requirements, UI, API запускай.
```

- По ходу стадий отвечать на вопросы агента. Остановка стадии (нет входа, ждёт подтверждения `ASSUMPTION`) — правильное поведение: дать недостающую информацию или отложить работу, но не разрешать «додумать ради завершения pipeline».
- На собранный список assumptions отвечать явно, по пунктам:

```text
По списку assumptions: ASSUMPTION про 3 попытки ввода кода подтверждаю —
это факт. Длину кода не выдумывай, оставь TBD: уточню у команды
безопасности.
```

### Результат сценария

Финальный отчёт оркестратора содержит: выполненные стадии, созданные и изменённые файлы, сводные списки `ASSUMPTION` и `TBD`, итог review. Сверить с чеклистом «Что проверять в каждом ответе агента». Дальше — Сценарий 5 (работа с находками review), затем Сценарий 6 (коммит).

## Сценарий 2. Отдельный документ

### Когда

Запрос укладывается в один документ — работает специализированный skill напрямую, без оркестратора. Правило выбора — раздел «Как определить нужный skill» в [AGENTS.md](AGENTS.md); границы каждого skill — секции «Когда использовать» / «Когда не использовать» его `SKILL.md`.

### Промпты

```text
Формализуй требования для feature password-recovery по её product.md.
Работай только с requirements.md — ui.md и api.md не трогай.
```

```text
Опиши API feature password-recovery: два endpoint — запрос кода и проверка
кода с установкой нового пароля. Формат ошибок дам после черновика,
пока помечай TBD.
```

### Точки контроля

- Skill останавливается без входов (например, нет `product.md` для формализации требований). Это правильное поведение: сначала создать вход отдельным промптом или через Сценарий 1, а не заставлять агента обходить остановку.
- Review нужен и после одного документа (раздел «Когда запускать review» в [AGENTS.md](AGENTS.md)) — Сценарий 5.

## Сценарий 3. Правка существующего draft/review-документа

### Когда

- Любые правки `draft`- и `review`-документов.
- MINOR-правки `approved`-документов: опечатки, ссылки, формулировки без изменения смысла. Порог — раздел «Изменение утверждённых документов» в [CONTRIBUTING.md](CONTRIBUTING.md).

Содержательное изменение `approved`-документа — Сценарий 4.

### Промпты

```text
В docs/features/password-recovery/requirements.md измени FR-003: интервал
повторного запроса кода — 60 секунд (подтверждённый факт, раньше был TBD).
Обнови связанные UI/API-требования и traceability. Больше ничего не меняй.
```

```text
Добавь в requirements.md feature password-recovery требование: после
3 неверных вводов кода сессия восстановления блокируется. Число 3 — факт
от product owner. Существующие требования не переформулируй.
```

### Как итерироваться

Формула точной правки: ID или цитата текущего текста, что не так, как должно быть, источник факта.

```text
FR-004 сформулирован неатомарно: запрос кода и проверка кода склеены
в одном требовании. Разбей на два; нумерацию существующих требований
не меняй.
```

Промпты без критерия готовности — «улучши», «перепиши получше», «наведи порядок» — не использовать: они провоцируют переписывание документа целиком и расширение scope.

### Точки контроля

- Diff минимален: изменено только запрошенное (правило минимального изменения — [CONTRIBUTING.md](CONTRIBUTING.md)).
- Существующие ID сохранены; cross-reference и traceability обновлены.
- Статус и версия изменённого документа — по правилам [schemas/README.md](schemas/README.md).

## Сценарий 4. Изменение approved-документа (change proposal)

### Когда обязателен proposal

При содержательном изменении `approved`-документа: добавление, изменение или удаление требований. Порог — раздел «Изменение утверждённых документов» в [CONTRIBUTING.md](CONTRIBUTING.md), процесс — [skills/change-management/SKILL.md](skills/change-management/SKILL.md).

### Этап 1. Создать proposal

```text
Нужно содержательно изменить утверждённый requirements.md feature
password-recovery: код теперь доставляется по SMS или e-mail на выбор
пользователя. Подготовь change proposal, сами целевые документы не трогай.
```

Проверить в результате:

- дельты разложены по ADDED / MODIFIED / REMOVED;
- в MODIFIED «Было:» — дословная текущая формулировка (сверить с документом);
- новые требования — placeholders `<TYPE>-NEW-<n>`, реальные ID не присвоены;
- неподтверждённые значения внутри дельт помечены `ASSUMPTION`/`TBD`.

### Этап 2. Решение человека

Единственная ручная правка файлов в этом workflow: человек сам выставляет решение в `proposal.md` — `## Status: approved` (или `rejected`) в теле и `status` в frontmatter. Агент не применяет `proposed`-proposal и не «дозревает» его статус.

### Этап 3. Применить proposal

```text
Proposal docs/changes/password-recovery-email-otp/proposal.md я утвердил
(Status: approved). Примени его.
```

Проверить в результате:

- секция Assigned IDs заполнена: каждый placeholder получил реальный ID;
- целевые документы: MAJOR bump версии, статус `review`;
- REMOVED-требования помечены `deprecated`, не удалены;
- директория proposal перенесена в `docs/changes/archive/`;
- review прогнан, отчёт передан целиком.

Повторный перевод целевых документов в `approved` — отдельное решение человека (Сценарий 6).

## Сценарий 5. Ревью и работа с замечаниями

### Когда запускать

После содержательного изменения requirements/ui/api/technical, перед переводом документа в `approved` и в конце любой сессии с изменениями. Полный список — раздел «Когда запускать review» в [AGENTS.md](AGENTS.md).

### Промпт

```text
Прогони documentation-review по feature password-recovery.
```

### Как читать отчёт

Формат отчёта — [skills/documentation-review/SKILL.md](skills/documentation-review/SKILL.md). Что означают находки для человека:

- `ERROR` — нарушение правил: битая ссылка, противоречие, непокрытое требование, подозрение на галлюцинацию. Требует решения до коммита.
- `WARNING` — качество: неатомарность, неизмеримая формулировка, отклонение от glossary. Решить: исправить сейчас или осознанно отложить.
- Четыре итоговых списка (Unresolved TBD, Unconfirmed assumptions, Broken references, Coverage gaps) — открытые вопросы к человеку, а не дефекты.

### Работа с находками

Review сам ничего не исправляет; решение по каждой находке принимает человек, исправления заказываются промптом пишущему skill:

```text
По отчёту review: ERROR про непокрытый FR-007 исправь — добавь
API-требование на проверку кода. WARNING про синоним «одноразовый код»
пока не трогай: сначала внесу термин в glossary отдельной задачей.
```

- Находку допустимо мотивированно отклонить — причина фиксируется в ответе агенту.
- После исправлений — повторный review затронутых документов.

## Сценарий 6. Финальная проверка и коммит

### Проверка

```text
Запусти node scripts/validate-docs.mjs. Есть ошибки — исправь и запусти
снова, покажи итоговый вывод.
```

Затем прочитать diff глазами — последняя линия защиты от выдуманных значений:

```text
Покажи git status и git diff по docs/features/password-recovery/.
```

### Чеклист перед коммитом

- [ ] `node scripts/validate-docs.mjs` — exit code `0`.
- [ ] Review прогнан после последнего содержательного изменения.
- [ ] На каждый `ASSUMPTION` дан ответ; оставшиеся `TBD` оставлены осознанно.
- [ ] Статусы и версии корректны; `approved` не появился без решения человека.
- [ ] Diff прочитан; в нём только запрошенное изменение.
- [ ] Изменения — один логический блок; иначе разбить на несколько коммитов.

### Коммит

```text
Закоммить изменения по feature password-recovery одним коммитом
с сообщением по конвенции из CONTRIBUTING.md.
```

Формат сообщения — раздел «Коммиты» в [CONTRIBUTING.md](CONTRIBUTING.md).

### Перевод в approved

Отдельное действие и отдельный коммит, после review без блокирующих находок:

1. Человек сам меняет `status` документа в frontmatter на `approved` (правила статусов и версий — [schemas/README.md](schemas/README.md)).
2. Запустить `node scripts/validate-docs.mjs`.
3. Закоммитить отдельным коммитом.

## Сценарий 7. Сверка документации с кодом

### Когда запускать

Когда код сервисов подключён в `services/` и нужно узнать не «как документация выглядит», а «совпадает ли она с реальностью»: перед переводом feature в `approved`, после крупного изменения кода, перед написанием `technical.md`.

Сценарий 5 (`documentation-review`) проверяет документацию саму по себе — противоречия между документами, качество формулировок, терминологию. Он не открывает код. Сверку документации с кодом делает только этот сценарий.

### Подключение кода

Без кода прогон возможен, но бессмысленен: все вердикты будут `unverifiable`. Подключить:

```bash
# вариант 1: через repos.json (список сервисов команды)
npm run pull

# вариант 2: симлинк на локальную копию
ln -s /path/to/service services/<service-name>
```

Имя сервиса — kebab-case, совпадает с компонентом в `docs/architecture/components.md` (подробности — [services/README.md](services/README.md)).

### Промпт

```text
Сверь документацию feature password-recovery с кодом в services/.
Нужны обе стороны: какие требования не реализованы или не покрыты тестами
и что код делает сверх спеки.
```

### Как читать отчёт

Отчёт — в `reports/verification/<дата>-<scope>.md`, в Git не попадает. Формат — [skills/spec-verification/SKILL.md](skills/spec-verification/SKILL.md). Что означают вердикты для человека:

- `contradicted` и секция Conflicts — высший приоритет: код и утверждённое требование расходятся. Решает человек, что из них правда; правка `approved`-документа идёт через Сценарий 4.
- `not-implemented` — требование не реализовано. Задача на разработку, а не на документацию.
- `undecided-in-spec` — самое ценное: **код отвечает на открытый `TBD` или `ASSUMPTION` спеки**. Подтвердить значение и закрыть вопрос (Сценарий 3).
- `undocumented` — код делает то, чего не описывает ни одно требование. Либо завести требование, либо признать поведение внутренним.
- `unverifiable` с причиной `requires-runtime-measurement` — норма для количественных NFR; с причиной `spec-underspecified` или `requires-human-judgement` — сигнал, что требование сформулировано непроверяемо ([rules/requirements.md](rules/requirements.md)).
- `verified coverage` считается без `unverifiable` в знаменателе — метрика не улучшается за счёт непроверяемых требований.

### Работа с находками

Skill ничего не изменяет: ни `docs/`, ни `services/`. Каждая находка — вход для человека:

```text
По отчёту сверки: значение интервала повторной отправки из кода (90 секунд)
подтверждаю как факт — закрой TBD в BR-002. Недокументированный эндпоинт
отмены сессии пока не описывай: решу, публичный он или внутренний.
```

- Требование остаётся source of truth: спека под код не переписывается. Расхождение либо закрывается изменением требования (осознанно, через Сценарий 3 или 4), либо задачей на исправление кода.
- Вердикт допустимо мотивированно оспорить — если агент не нашёл реализацию, а она есть, назвать файл: в отчёте есть журнал выполненных запросов, по нему видно, чего он не искал.
- После изменений документации — повторный прогон Сценария 5, затем при необходимости Сценария 7.

## Если что-то пошло не так

- Агент вписал конкретное значение без источника — указать на [rules/ai-guardrails.md](rules/ai-guardrails.md) и потребовать заменить значение на `TBD`/`ASSUMPTION` либо назвать источник.
- Агент переписал документ целиком — откатить (`git checkout -- <файл>`) и повторить промпт с явным ограничением scope.
- `validate-docs` падает — скопировать вывод в промпт целиком: формат `файл:строка [КОД] сообщение` самодостаточен для исправления.
- Агент сам поставил `approved` или применил неутверждённый proposal — откатить изменение и указать на нарушение: статусы решений выставляет только человек.
- Агент выбрал не тот skill (оркестратор для точечной правки или наоборот) — назвать нужный skill явно (routing — [AGENTS.md](AGENTS.md)).
- При сверке с кодом агент объявил требование нереализованным, а оно реализовано — посмотреть журнал запросов в отчёте и назвать файл: вердикт `not-implemented` обязан опираться на записанный поиск, а не на его отсутствие.
- При сверке с кодом агент предложил переписать требование под код — отклонить: направление разрешения расхождений задано в [AGENTS.md](AGENTS.md), раздел «Source of truth».
